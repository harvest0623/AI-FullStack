## 一、什么是 RAG

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种架构模式：**在让 LLM 生成回答之前，先从外部知识库检索出与问题相关的上下文，再把"问题 + 上下文"一起交给 LLM，让它基于这些证据作答。**

```
用户提问 ──▶ ① 检索（Retrieval）──▶ 取出相关上下文
                            │
         ┌──────────────────┘
         ▼
      ② 增强（Augment）：把上下文拼进 Prompt
         │
         ▼
      ③ 生成（Generation）：LLM 基于上下文作答
```

一句话概括：**"先查资料，再回答。"** 这是 RAG 与纯 LLM（直接作答）最本质的区别。

---

## 二、为什么需要 RAG

原生 LLM（仅靠参数记忆）有三大硬伤，RAG 恰好对症：

| LLM 痛点 | 说明 | RAG 对策 |
|---------|------|---------|
| **幻觉** | 模型"一本正经地编造" | 基于检索到的真实上下文作答，减少编造 |
| **时效性** | 训练数据截止在某个时间点 | 检索最新知识库，实时获取新信息 |
| **私有数据** | 训练数据不含企业私有资料 | 检索私有知识库，让模型"懂你的数据" |

除此之外，RAG 还带来工程上的好处：
- **可更新性**：知识变了，更新检索库即可，无需重新训练
- **可溯源**：回答可附带来源引用（"来自文档 X"），增强可信度
- **可解释**：能明确回答"依据了哪些资料""

## 三、RAG vs 微调 vs 长上下文

这是决策时最容易纠结的三选一，先看对比：

| 维度 | RAG | Fine-tuning 微调 | 长上下文 |
|------|-----|-----------------|----------|
| 知识来源 | 外部检索库 | 模型参数 | 直接塞进 Prompt |
| 更新成本 | 低（改库即可） | 高（重训） | 低（改 Prompt） |
| 幻觉 | 较低 | 中 | 低（有原文）但易失真 |
| 溯源能力 | 强 | 无 | 中 |
| 成本（每查询） | 中（检索+生成） | 低 | 高（全塞上下文） |
| 上下文长度 | 受限长度 | 无限制 | 受窗口限制 |
| 适用场景 | 私有数据/需更新/需溯源 | 学习特定风格/能力 | 单次大量资料 |

**结论**：
- 想**注入私有数据 / 频繁更新 / 需要溯源** → 用 **RAG**
- 想**学到新的行为/风格/专业知识** → 用**微调**
- 两者也常**组合使用**（微调提升指令遵循 + RAG 注入知识）

## 四、参考：RAG 演进史

理解演进脉络，你就知道我们后面每天在解决什么问题：

```
Naive RAG（朴素）     Advanced RAG（高级）      Modular RAG（模块化）
┌──────────────┐   ┌──────────────────┐   ┌──────────────────────┐
│ 切块+嵌入+检索 │-> │ +重排 +改写        │-> │ 可插拔模块 + Agent    │
│ +生成          │   │ +HyDE +混合检索    │   │ 路由/记忆/编排        │
└──────────────┘   └──────────────────┘   └──────────────────────┘
  痛点：召回粗        对症：提升检索质量       对症：复杂场景编排
```

- **Naive RAG**：朴素的"切块→向量→检索→生成"，实现简单但召回质量不稳。
- **Advanced RAG**：在检索前后做优化（重排、查询改写、HyDE、混合检索），是工程落地主力。
- **Modular RAG**：各步骤拆成可插拔模块，甚至引入 Agent 自动编排（即 Agentic RAG）。

本板块按此演进入手：Day02 先跑通 Naive RAG，Day03-08 升级到 Advanced RAG，Day09-12 走向生产级架构。

## 五、RAG 的适用与不适用场景

### 适合用 RAG

- 私有文档问答（企业知识库、合同、政策）
- 需要**实时/最新**信息的场景（新闻、行情）
- 需要**溯源引用**的场景（客服、合规、金融）
- 多来源资料的综合问答

### 不适合 / 需谨慎用 RAG

- 纯开放域闲聊（无固定知识源）
- 需要深度推理/创造性写作（检索帮助有限）
- 资料极少且无私有数据（直接用模型更简单）
- 实时性要求极高 + 检索延迟不可接受时

> 判断口诀：**有没有"需要查的东西"？能不能"查"到？查完后模型能否"用"好？** 三者皆为是，才适合 RAG。

## 六、RAG 的失败模式与质量瓶颈

提前认识这些"坑"，后续每天都是在填坑：

### 检索层（Retrieval）

| 失败模式 | 说明 | 对应解决（后续 Day） |
|---------|------|---------------------|
| 语法不匹配 | 用户口语 vs 文档书面语，向量相似度低 | 查询改写 / HyDE（Day07） |
| 语义鸿沟 | 问题与文档不在同一表达层面 | HyDE / 语义切块（Day04/07） |
| 切块不当 | 一块内容被切碎，语义断裂 | 切块策略（Day03） |
| 上下文漂移 | 问题需要全文/前后文，单块不够 | 父块检索 / 窗口（Day03/09） |

### 生成层（Generation）

| 失败模式 | 说明 | 对应解决 |
|---------|------|---------|
| 幻觉 | 脱离上下文编造 | 忠实性评估 + 约束 Prompt（Day10） |
| 答非所问 | 检索到但与问题无关 | 相关性评估 + 重排（Day06/10） |
| 上下文冲突 | 多个来源互相矛盾 | 冲突处理（Day09） |

### 可观测性

评估不可见 → 无法知道哪里坏了 → 无法优化。**评估劣后于一切**（Day10 专门讲）。

> **DataIQ 公司**是一家金融科技企业，积累了数千份制度文档、产品资料与合规报告。员工经常提问如"我们的报销标准是什么？""新产品支持哪些支付方式？"。直接用 LLM 答不上来（私有数据），逐份翻文档不现实。于是我们用 **RAG 构建企业知识库问答系统**：把所有文档入库，员工提问时自动检索相关段落并生成带依据的回答。

## 关键知识点总结

1. **RAG = 检索 + 生成**：先查资料，再回答。
2. **三大动机**：抗幻觉、提时效、接私有数据。
3. **三选一**：注入知识用 RAG，学能力用微调，短时大量资料用长上下文。
4. **演进路线**：朴素 → 高级 → 模块化/Agentic。
5. **两大瓶颈**：检索召回质量 + 生成忠实性。
