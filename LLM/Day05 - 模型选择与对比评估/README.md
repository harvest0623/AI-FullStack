# Day05 - 模型选择与对比评估

LLM 生态已从"GPT 一家独大"演进为"百模齐放"：闭源有 GPT-4o、Claude 3.5、Gemini 1.5 三足鼎立，开源有 Llama 3、Qwen 2.5、DeepSeek 各显神通。面对数十个可选模型，AI 工程师每天都要回答同一个问题——"这个任务该用哪个模型？"。本章从能力维度、价格、延迟、上下文窗口、部署方式五个角度系统对比主流模型，给出可落地的选型决策框架、模型路由策略与 A/B 测试方法论，并提供多模型对比、基准测试、成本延迟分析的完整工程化代码。记住一条铁律：**没有最好的模型，只有最适合的模型**，模型选型是 AI 工程师的核心决策。

## 学习目标

完成本章后，你应能：

1. 从推理、代码、创作、多语言、多模态、指令遵循、上下文窗口七个维度评估任意 LLM 的能力。

4. 运用四步决策框架（任务类型 → 约束条件 → 候选评估 → A/B 测试）完成模型选型。
5. 解读 MMLU / HumanEval / GSM8K / MT-Bench / AlpacaEval 等主流基准，并理解其局限性。
6. 实现基于规则与基于复杂度判断的二级模型路由。
7. 用 LLM-as-Judge 与人工评分对比多模型输出质量。
8. 测量 TTFT、生成速度、Token 消耗与成本，并估算月度开销。

## 理论知识讲解

### 5.1 模型能力维度

评估一个 LLM 不能只看"聪不聪明"，而要拆解为七个可量化的能力维度。

| 维度 | 评估问题 | 代表基准 | 典型强模型 |
|------|---------|---------|-----------|
| 推理能力 | 多步逻辑、数学计算、因果推断 | GSM8K / MATH | o1 / Claude 3.5 / GPT-4o |
| 代码能力 | 生成、调试、解释、重构代码 | HumanEval / MBPP | Claude 3.5 Sonnet / GPT-4o |
| 创作能力 | 文案、故事、创意写作 | MT-Bench / AlpacaEval | Claude 3.5 / GPT-4o |
| 多语言能力 | 中英及小语种支持 | MGSM / FLORES | Qwen 2.5 / GPT-4o |
| 多模态能力 | 图像、音频、视频理解 | MMMU / MathVista | GPT-4o / Gemini 1.5 |
| 指令遵循 | 格式控制、约束遵守 | IFEval / AlpacaEval | GPT-4o / Claude 3.5 |
| 上下文窗口 | 长文本处理能力 | NeedleInHaystack | Gemini 1.5 Pro / Claude 3.5 |

**关键认知**：能力维度之间并非完全正相关。例如 o1 推理能力极强但响应慢、价格高；GPT-4o-mini 速度快但推理深度有限。选型本质是多目标优化。

### 5.2 闭源模型对比

#### 5.2.1 OpenAI 阵营

- **GPT-4o**：2024 年旗舰，"o"代表 omni 全模态。综合能力最强，支持文本+图像+音频输入输出，速度快（约 100 tokens/s），128K 上下文。**通用首选**。
- **GPT-4o-mini**：小尺寸版本，速度极快、价格仅为 GPT-4o 的 1/30 左右。**高并发、低成本场景首选**。
- **GPT-4 Turbo**：上一代旗舰，推理强、128K 长上下文，但在多数基准上已被 GPT-4o 超越。**遗留兼容场景**。
- **o1 / o1-mini**：推理模型，内置思考链（Chain-of-Thought），适合数学、编程、科研等复杂推理。响应慢、价格高，**复杂推理专用**。

#### 5.2.2 Anthropic 阵营

- **Claude 3.5 Sonnet**：代码、长文本、写作能力突出，200K 上下文，速度快、价格适中。**代码与长文档场景首选**。
- **Claude 3 Opus**：Claude 3 系列中推理最强，但已被 3.5 Sonnet 在多数场景超越，且价格更高。**重推理遗留场景**。

#### 5.2.3 Google 阵营

- **Gemini 1.5 Pro**：1M+ 超长上下文（实测可达 2M），全模态（文本+图像+音频+视频）。**超长文档、视频分析首选**。

#### 闭源模型综合对比表

| 模型 | 上下文 | 多模态 | 输入价 ($/1M tok) | 输出价 ($/1M tok) | 强项 | 弱项 |
|------|--------|--------|-------------------|-------------------|------|------|
| GPT-4o | 128K | 文+图+音 | 2.5 | 10 | 综合最强、速度快 | 长上下文不如 Gemini |
| GPT-4o-mini | 128K | 文+图 | 0.15 | 0.6 | 性价比之王 | 复杂推理弱 |
| GPT-4 Turbo | 128K | 文+图 | 10 | 30 | 推理强 | 已被 4o 超越、价高 |
| o1 | 200K | 文 | 15 | 60 | 深度推理 | 慢、贵 |
| o1-mini | 128K | 文 | 3 | 12 | 推理性价比 | 仅文本 |
| Claude 3.5 Sonnet | 200K | 文+图 | 3 | 15 | 代码/长文/写作 | 多模态弱于 4o |
| Claude 3 Opus | 200K | 文+图 | 15 | 75 | 推理 | 性价比低 |
| Gemini 1.5 Pro | 1M+ | 全模态 | 1.25 | 5 | 超长上下文/视频 | 生态弱于 OpenAI |

> 价格为示例值，请以官方最新定价为准。

### 5.3 开源模型对比

#### 5.3.1 主流开源家族

- **Llama 3 / 3.1（8B / 70B / 405B）**：Meta 出品，全球最流行的开源生态。3.1 版本上下文扩到 128K，能力对标 GPT-4 级别。**通用开源首选**。
- **Qwen 2 / 2.5（7B / 72B）**：阿里出品，中文能力最强的开源系列，多尺寸覆盖端到云。**中文场景首选**。
- **Mistral / Mixtral 8x7B**：法国 Mistral AI，MoE 架构，推理效率高、激活参数少。**高效推理场景**。
- **DeepSeek V2 / V3**：国产推理能力强、API 价格极低（V3 输入 $0.27/1M、输出 $1.1/1M），MoE 架构。**低成本高性能场景**。

#### 开源模型对比表

| 模型 | 参数量 | 上下文 | 中文能力 | 显存需求（INT4） | 适用场景 |
|------|--------|--------|---------|-----------------|---------|
| Llama 3.1 8B | 8B | 128K | 一般 | ~6GB | 端侧/开发测试 |
| Llama 3.1 70B | 70B | 128K | 一般 | ~40GB | 生产通用 |
| Llama 3.1 405B | 405B | 128K | 良好 | ~230GB | 顶级开源推理 |
| Qwen 2.5 7B | 7B | 128K | 优秀 | ~5GB | 中文端侧 |
| Qwen 2.5 72B | 72B | 128K | 优秀 | ~42GB | 中文生产 |
| Mixtral 8x7B | 47B(激活13B) | 32K | 一般 | ~25GB | 高效推理 |
| DeepSeek V3 | 671B(激活37B) | 128K | 优秀 | ~200GB | 低成本高性能 |

#### 开源模型适用场景

- **本地部署**：数据隐私敏感、离线环境、边缘设备。
- **微调定制**：需要领域适配、风格定制。
- **成本控制**：高 QPS 场景下自建比 API 更省。

### 5.4 模型选型决策框架

选型不是"挑最强的"，而是"挑最匹配的"。推荐四步决策法。

#### 第一步：明确任务类型

| 任务类型 | 典型问题 | 关键能力 |
|---------|---------|---------|
| 对话 | 客服、闲聊 | 指令遵循、流畅性 |
| 分类 | 情感分析、意图识别 | 指令遵循、稳定性 |
| 抽取 | 实体、关系、字段抽取 | 格式控制、指令遵循 |
| 生成 | 文案、故事、摘要 | 创作能力 |
| 推理 | 数学、逻辑、因果 | 推理能力 |
| 代码 | 生成、调试、解释 | 代码能力 |

#### 第二步：确定约束条件

- **成本**：单次请求预算、月度总预算。
- **延迟**：首字延迟 TTFT 上限、总延迟上限。
- **隐私**：是否允许数据出域？是否需要本地部署？
- **部署方式**：API 调用 / 私有化部署 / 端侧。

#### 第三步：评估候选模型

从能力匹配度、价格、速度、上下文窗口、生态支持五个角度评估 2-3 个候选。

#### 第四步：A/B 测试验证

线上灰度对比，用真实业务指标（用户满意度、任务完成率、成本）决策，而非仅看基准分数。

#### 决策树图示

```
                    ┌─ 是否隐私敏感？ ──→ 是 ──→ 开源模型本地部署
                    │                        （Llama 3 / Qwen 2.5）
                    │
   任务类型 ──→ ┌───┴─── 否 ──→ ┌─ 是否超长上下文（>200K）？
                │                │   │
                │                │   ├─ 是 ──→ Gemini 1.5 Pro
                │                │   │
                │                │   └─ 否 ──→ ┌─ 是否复杂推理？
                │                │              │
                │                │              ├─ 是 ──→ o1 / Claude 3.5
                │                │              │
                │                │              └─ 否 ──→ ┌─ 是否高并发低成本？
                │                │                          │
                │                │                          ├─ 是 ──→ GPT-4o-mini
                │                │                          │       / Qwen-Turbo
                │                │                          │
                │                │                          └─ 否 ──→ GPT-4o
                │                │                                   / Claude 3.5
```

### 5.5 能力评估基准

| 基准 | 评估内容 | 题量 | 说明 |
|------|---------|------|------|
| MMLU | 多任务语言理解 | 57 学科 | 综合知识广度 |
| HumanEval | 代码生成 | 164 题 | 函数级代码正确性 |
| GSM8K | 小学数学推理 | 8500 题 | 多步数学推理 |
| MT-Bench | 多轮对话 | 80 题 | 多轮对话质量（GPT-4 评分） |
| AlpacaEval | 指令遵循 | 805 题 | 与参考答案胜率 |
| MATH | 竞赛数学 | 12500 题 | 高难度数学 |
| IFEval | 指令遵循 | 540 题 | 格式约束遵守 |

**基准的局限性**：

1. **数据污染**：训练集可能包含测试集，分数虚高。
2. **场景偏差**：基准任务与真实业务场景存在差距。
3. **长度偏好**：MT-Bench / AlpacaEval 倾向更长回答。
4. **无法覆盖主观质量**：语气、风格、安全等难以量化。

结论：基准用于初筛，最终决策靠真实业务 A/B 测试。

### 5.6 输出质量对比方法

#### 5.6.1 相同输入对比

固定一组测试输入，调用多个模型，并排展示输出做人工或自动对比。

#### 5.6.2 LLM-as-Judge

用强模型（通常是 GPT-4）作为裁判，按维度（准确性、相关性、流畅性）给候选输出打分。

```text
裁判 Prompt 示例：
你是一个严格的评审专家。请从准确性、相关性、流畅性三个维度
对下面两个回答打分（1-10），并给出胜者。
用户问题：{question}
回答 A：{answer_a}
回答 B：{answer_b}
```

**注意事项**：裁判模型有位置偏好（倾向 A），需随机打乱顺序；对长输出有偏好。

#### 5.6.3 人工评分

设计评分量表（Likert 5 级），多名标注员盲评，计算一致性（Cohen's Kappa）。金标准但成本高。

### 5.7 成本与延迟对比

#### 5.7.1 成本要素

- **输入 Token 单价**：处理 prompt 的费用。
- **输出 Token 单价**：生成回答的费用（通常是输入的 3-4 倍）。
- **总成本**：`输入数 × 输入价 + 输出数 × 输出价`。

#### 5.7.2 延迟要素

| 指标 | 全称 | 含义 | 用户体验关键 |
|------|------|------|------------|
| TTFT | Time To First Token | 首字延迟 | 流式场景最关键 |
| 生成速度 | Tokens/s | 每秒生成 Token 数 | 长输出体验 |
| 总延迟 | Total Latency | 请求发出到完成 | 非流式场景关键 |

#### 5.7.3 成本延迟对比表

| 模型 | 输入价 ($/1M) | 输出价 ($/1M) | TTFT (s) | 速度 (tok/s) | 1K 请求成本（1K in + 1K out） |
|------|--------------|--------------|----------|--------------|------------------------------|
| GPT-4o | 2.5 | 10 | 0.5 | 100 | $0.0125 |
| GPT-4o-mini | 0.15 | 0.6 | 0.3 | 150 | $0.00075 |
| o1 | 15 | 60 | 5+ | 50 | $0.075 |
| Claude 3.5 Sonnet | 3 | 15 | 0.6 | 90 | $0.018 |
| Gemini 1.5 Pro | 1.25 | 5 | 0.8 | 80 | $0.00625 |

> 数据为典型值，实际因负载波动。

### 5.8 模型路由策略

单一模型难以兼顾成本与质量，**模型路由**（Model Routing）是工程化必经之路。

#### 5.8.1 静态路由（规则路由）

按任务类型、输入长度等显式规则分配模型：

| 任务特征 | 路由目标 |
|---------|---------|
| 简单分类 / 意图识别 | GPT-4o-mini / Qwen-Turbo |
| 复杂推理 / 多步逻辑 | GPT-4o / Claude 3.5 / o1 |
| 代码生成 / 调试 | Claude 3.5 Sonnet / GPT-4o |
| 长文本（>100K） | Gemini 1.5 Pro / Claude 3.5 |
| 闲聊 / 简单问答 | GPT-4o-mini |

#### 5.8.2 动态路由（复杂度判断）

先用小模型（便宜）判断输入复杂度，再决定是否升级到大模型：

```text
1. 调用 GPT-4o-mini 判断复杂度（简单/中等/复杂）
2. 简单 → 直接由 mini 回答
3. 中等 → 升级到 GPT-4o
4. 复杂 → 升级到 o1 或 Claude 3.5
```

**优势**：兼顾成本与质量，相比"全用大模型"可降本 50-80%。

**代价**：多一次小模型调用（约 0.3s + 极低成本），需评估是否值得。

#### 5.8.3 路由维度

- **输入长度**：< 1K → mini；1K-32K → 标准；> 32K → 长窗口模型。
- **任务类型**：通过 system prompt 或意图识别分类。
- **复杂度**：是否含数学/多步推理/代码。
- **用户分级**：VIP 用户用大模型，免费用户用小模型。

### 5.9 A/B 测试模型选型

#### 5.9.1 流程

1. **流量分配**：按用户 ID 哈希分桶，确保同一用户始终在同一组。
2. **评估指标**：业务指标（任务完成率、用户满意度、留存）+ 工程指标（延迟、成本、错误率）。
3. **统计显著性**：样本量足够（通常 >1000/组），p < 0.05 才下结论。

#### 5.9.2 常见陷阱

- **过早停止**：样本不足就下结论，受偶然波动影响。
- **指标单一**：只看质量不看成本，或反之。
- **辛普森悖论**：分桶不均导致整体结论与分组矛盾。

## 实战练习

### 练习 1：多模型对比你的业务场景

选择一个真实业务问题（如"客服问答"或"代码 review"），用 `01_model_comparison.py` 对 GPT-4o、GPT-4o-mini、Claude 3.5 Sonnet 三个模型在同一组 10 条输入上对比。从准确性、流畅性、成本三个维度给出推荐结论。

**提示**：参考 `ModelComparator`，记录每条的响应时间和 Token 数。

### 练习 2：构建业务基准测试集

针对你的业务领域，设计 20 道测试题（分类 5 + 推理 5 + 代码 5 + 创作 5），用 `02_benchmark_runner.py` 跑两个模型，对比通过率与平均延迟，输出 Markdown 报告。

**提示**：测试题需有"期望输出"或"评分要点"，便于自动判分。
