## 二、理论知识

### 2.1 ReAct 为什么会出错

- 工具本身出错（参数错、无权限、超时、第三方挂掉）。
- 模型生成了**不存在的工具**或**非法 JSON**。
- 网络/API 瞬时故障。
- 模型陷入死循环或越跑越偏。

### 2.2 把异常变成 Observation

正确做法是**不让脚本崩溃**，把错误文本作为 Observation 回填：

```python
try:
    result = tool.run(**args)
    obs = str(result)
except Exception as e:
    obs = f"调用 {name} 出错: {e}，请检查参数后重试"
history.append({"role": "tool", "content": obs})
```

模型读到错误后，通常会修正参数或换工具。

### 2.3 工具层 try/except

在 Tool.run 上加统一兜底（可选，建议调用方处理）：

```python
def safe_run(tool, **kw):
    try:
        return tool.run(**kw)
    except KeyError:
        return "参数缺失"
    except Exception as e:
        return f"异常: {e}"
```

### 2.4 非法 JSON 参数兜底

若模型给的 arguments 不是合法 JSON（文本协议场景），解析失败就回一条提示让模型重发：

```python
Action Input: [不是 json]
---
Observation: 参数无法解析, 请以合法 JSON 重新提供 Action Input。
```

### 2.5 调用次数与时间上限

- 工具调用次数上限（如 5 次），防止滥用。
- 总步数上限（max_steps）。
- 可选硬超时（timeout）。

```python
if tool_calls_done >= max_tool_calls:
    return fallback("已达工具调用上限，停止调用")
```

### 2.6 优雅降级与最终兜底回答

全部失败时给用户一个**不启动更多工具**的诚实回答：

> 「抱歉，暂时无法获取数据（工具连续失败）。你可以稍后再试或直接告诉我更多信息。」

千万不要崩溃或死循环。

## 三、核心概念解析

### 3.1 反馈-自纠闭环

Observation 不仅承载成功结果，也承载失败原因。**让模型读到错误 = 让模型有机会修正**，这比把错误抛到 UI 更有用。

### 3.2 可信度分层处理

- **高可信**（成功结果）：直接继续。
- **中可信**（可重试的错误）：提示模型自纠，计入重试次数。
- **低可信**（连续失败/死循环）：触发兜底，停止。

---

## 四、关键知识点总结

- **异常 → Observation**，而非崩溃。
- **工具/参数错误**在下一轮自纠。
- **非法 JSON** 提示模型重发。
- **次数/时间上限**是硬约束。
- **兜底回答**保证体面收场。
