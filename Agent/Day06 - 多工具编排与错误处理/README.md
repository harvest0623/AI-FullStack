## 二、工具选择的准确性

10 个工具时模型选择尚可；50 个工具时错误率显著上升。优化手段：

| 手段 | 做法 |
|------|------|
| **描述精修** | 每个工具描述写清"何时用/何时不用"（负面示例很重要） |
| **工具分组** | 按域分组（数据组/沟通组/文件组），先路由到组再选工具（两级选择） |
| **动态注入** | 不把全部工具发给模型，按任务类型只给相关子集 |
| **命名规范** | 动词_宾语（`send_email`），杜绝含糊命名 |
| **提供"不用工具"出口** | 明确告知可以直答，避免硬凑工具 |

> 两级路由：`router` 先判断任务域（销售/客服/通用），再暴露该域的 5-8 个工具——把 50 选 1 变成 6 选 1。

## 三、并行工具调用

无依赖的调用应并行发起（接 Day05 DAG 思想）：

```
用户：对比三个区域的销量
模型（一次输出 3 个 tool_calls）：
  call_1: query_sales(region="north")
  call_2: query_sales(region="south")
  call_3: query_sales(region="east")
执行器：并发执行，结果按 tool_call_id 回填
模型：聚合三个结果给出对比结论
```

**关键工程点**：
1. **关联**：结果用 `tool_call_id` 对应回各自的调用（顺序无关）
2. **聚合**：把多个结果合并成一条结构化观察喂回模型
3. **超时**：并行调用整体设置超时，慢工具不能拖死整批
4. **部分失败**：一个失败不致命——回填错误，让模型决定重试还是跳过

## 四、错误分类与处理体系

| 错误类 | 例子 | 是否重试 | 处理 |
|--------|------|---------|------|
| **参数错误** | 类型/枚举/格式不对 | 改参数后可"重试" | 错误信息可指导，让模型修正 |
| **执行错误** | 服务 500、语法错 | 可重试（指数退避） | 上限 2-3 次 |
| **超时** | 工具卡死 | 换更短超时重试 1 次 | 再失败上报 |
| **权限/资源错误** | 403、配额耗尽 | **不重试** | 上报人工 |
| **幻觉错误** | 调用不存在的工具 | 不重试 | 返回可用清单 |

**重试策略三选一**：
```
A. 原参数退避重试   —— 执行错/超时（瞬时故障）
B. 换工具/换参数     —— 参数错/语义错（需要模型纠正）
C. 升级问用户       —— 权限错/信息不足（人力介入）
```

## 五、成本控制

Agent 的成本 = 步数 × 每步 token。失控点与对策：

| 预算项 | 失控表现 | 对策 |
|--------|---------|------|
| 步数 | 反复尝试不收敛 | `max_steps` 硬顶 |
| token | 上下文越滚越大 | 历史裁剪（Day04）+ 观察截断 |
| 工具调用 | 高价工具反复调 | 每任务调用上限 + 结果缓存 |
| 金额 | 单任务成本爆表 | 预算仪表 + 超限降级（简化回答/终止上报） |

> **缓存**：相同参数的工具调用结果可缓存（如同一周的销量查询），直接省一次执行与一轮往返。

## 九、小结

- **选择准确性**：描述精修 + 分组路由 + 动态注入，把 N 选 1 降维
- **并行编排**：无依赖调用并发执行，`tool_call_id` 关联回填，部分失败不致命
- **错误体系**：分类（参数/执行/超时/权限/幻觉）决定策略（改参数/退避/换工具/上报）
- **成本预算**：步数、token、调用数、金额四道闸，超限要"降级"而非"死掉"

**今日金句**：工具多不是能力，选得准才是；跑得快靠并行，跑得稳靠错误分类，跑得久靠预算控制。
