## 二、工具：Agent 的双手

没有工具的 Agent 只是 Chatbot。工具的质量**直接决定** Agent 的能力上限：

- 工具太少 → 任务做不了
- 工具描述差 → 模型选错工具
- 参数设计烂 → 模型传错参数
- 返回结果乱 → 模型读不懂观察

**核心认知**：模型从未"执行"工具——它只输出一个**意图**（工具名+参数的 JSON），执行永远在你的代码里。这就是 Function Calling 的本质。

---

## 三、工具定义：Schema 设计

一个生产级工具定义包含：

```python
{
    "name": "query_sales",                    # 动词开头、见名知义
    "description": "查询指定周次的销量数据...",   # 何时用/输入什么/返回什么
    "parameters": {                            # JSON Schema
        "type": "object",
        "properties": {
            "week": {
                "type": "string",
                "description": "周次，格式 YYYY-Www，如 2024-W03",
                "pattern": "^\\d{4}-W\\d{2}$"  # 格式约束
            }
        },
        "required": ["week"]
    }
}
```

### 设计规范

| 要素 | 好的做法 | 坏的做法 |
|------|---------|---------|
| name | `send_email`、`query_order` | `tool1`、`handle` |
| description | 说清"何时用+输入+输出+限制" | "发邮件" |
| 参数个数 | ≤5 个，超过就拆工具 | 十几个参数一把梭 |
| 枚举 | 用 `enum` 收敛取值 | 自由字符串猜格式 |
| 返回 | 结构化 JSON + 明确 error 字段 | 一坨自然语言 |

> **描述就是给模型的 API 文档**。模型选不选、用得好不好，八成取决于描述质量。

## 四、Function Calling 完整往返

```
 1. 注册        你的代码把工具清单(Schema)随消息发给模型
     │
 2. 决策        模型输出：我要调 query_sales(week="2024-W02")
     │          （注意：模型只是"说"，没执行）
 3. 校验        你的代码校验工具存在、参数合法
     │
 4. 执行        你的代码真正调用函数，拿到结果
     │
 5. 回填        把结果作为 tool 消息追加进对话
     │
 6. 再决策      模型看到结果 → 直答 or 继续调用下一个工具
```

- 步骤 2 的**幻觉**（编造不存在的工具/参数）必须靠步骤 3 拦截
- 步骤 6 说明工具调用天然是**循环**的——接上 Day02 的核心循环，就是一个完整 Agent

## 五、参数校验：防幻觉的第一道闸

模型输出的参数不可信，必须校验：

| 校验项 | 示例 | 失败处理 |
|--------|------|---------|
| 工具存在 | name 在注册表中 | 拒绝 + 告知可用工具 |
| 类型 | `week` 是 str | 拒绝 + 指出类型 |
| 必填 | required 都有 | 拒绝 + 列出缺失 |
| 枚举 | region ∈ {"north","south"} | 拒绝 + 给出合法值 |
| 格式 | 正则 YYYY-Www | 拒绝 + 示例格式 |

> **原则**：宁可让模型重试，不可让脏参数进入真实系统。错误信息要"可指导"——告诉模型哪里错了怎么改。

## 六、常见工具类型

| 类型 | 例子 | 注意 |
|------|------|------|
| 检索类 | 知识库查询、搜索 | RAG 就是检索工具 |
| 数据类 | SQL 查询、API 请求 | 只读/读写分权 |
| 计算类 | 计算器、统计 | LLM 算术弱，交给工具 |
| 操作类 | 发邮件、写文件 | 高危，需审批（Day09） |
| 代码类 | 执行 Python/SQL | 沙箱隔离必须 |

## 十、小结

- **模型只出意图，你负责执行**——Function Calling 的本质是"结构化的模型输出 + 你的安全执行"
- **描述即文档**：工具名/描述/Schema 的质量决定选用准确率
- **校验是第一道闸**：工具存在性 + 参数类型/必填/枚举/格式，脏参数绝不入系统
- **往返即循环**：注册→决策→校验→执行→回填→再决策，接上 Day02 就是完整 Agent

**今日金句**：工具描述是写给模型的 API 文档，参数校验是写给幻觉的防火墙。
