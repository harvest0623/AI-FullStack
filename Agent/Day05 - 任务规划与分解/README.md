## 二、为什么需要规划

纯 ReAct 是"走一步看一步"：每步只根据局部观察决策。

| 问题 | 表现 |
|------|------|
| 短视 | 绕远路：先查 A 再查 B，其实需要的是 C |
| 无全局感 | 忘记整体目标，陷入局部细节 |
| 长任务失控 | 30 步的活儿走一步看一步，很容易中途"迷路" |
| 难以并行 | 没有全局视图，看不出哪些步骤可以同时做 |

**规划式范式**：先让 LLM 产出完整计划（清单/图），再逐步执行——用一次"深谋"换全程"远虑"。

## 三、Plan-and-Execute 范式

```
        目标
         │
         ▼
  ┌──────────────┐
  │  Planner      │  产出：任务清单（有序步骤）
  └──────┬───────┘
         ▼
  ┌──────────────┐   执行失败/偏差    ┌──────────────┐
  │  Executor    │ ────────────────▶ │  Replanner   │
  │  逐步执行     │ ◀──────────────── │  修正计划     │
  └──────────────┘    新计划          └──────────────┘
         │
         ▼
       最终答案
```

### ReAct vs Plan-and-Execute

| 维度 | ReAct | Plan-and-Execute |
|------|-------|------------------|
| 决策粒度 | 每步重新决策 | 计划一次，逐步执行 |
| token 成本 | 每步都带全部历史 | 执行器只需当前步上下文 |
| 长任务 | 易迷失 | 有路线图 |
| 灵活性 | 高（随时改道） | 靠 Replan 补救 |
| 适用 | 探索型短任务 | 结构化长任务 |

> **实践主流是混合**：先出计划，执行小步时仍可用 ReAct 微调；计划失败时触发 Replan。

## 四、任务分解的两种形态

### 4.1 TODO 清单（线性）

```
1. 查询本月销量
2. 查询上月销量
3. 计算环比
4. 生成周报文本
```

- 适合：步骤天然串行
- 优点：直观、好实现（LangGraph 的 TODO 驱动即此）

### 4.2 DAG 依赖图（非线性）

```
digraph {
  查本月 -> 算环比;
  查上月 -> 算环比;
  算环比 -> 写报告;
  查竞品 -> 写报告;   // 与算环比并行
}
```

- 适合：步骤间有并行/依赖关系
- 优点：能并行（Day06）、拓扑序清晰
- 实现：节点 + 依赖集合，调度时只跑"依赖已满足"的节点

**分解原则**：
1. 每步都是**一次可验证的行动**（一个工具调用/一次判断）
2. 步骤间依赖**显式声明**，不靠隐式顺序
3. 粒度适中：太粗无法执行，太细浪费规划

## 五、动态重规划（Replan）

计划是预测，执行是现实。触发 Replan 的信号：

| 信号 | 例子 | 重规划动作 |
|------|------|-----------|
| 步骤失败 | 查询接口 404 | 换替代数据源，改后续步骤 |
| 观察与预期不符 | 销量为空 | 插入"先确认数据范围"步骤 |
| 目标变化 | 用户追加要求 | 合并新目标，重排剩余步骤 |

**Replan 的输入**：原计划 + 已完成步骤 + 失败/偏差观察 + 剩余目标。
**Replan 的输出**：新计划（保留已完成成果，只重排未来）。

> 工程上要限制 Replan 次数（如 ≤2 次），否则"反复改道"本身就是失控。

## 九、小结

- **规划是全局视图**：先出计划再执行，长任务不迷路
- **两种形态**：TODO 清单（线性直观）/ DAG（显式依赖、可并行）
- **Replan 是安全网**：失败/偏差时"保留成果 + 重排未来"，且限制次数
- **粒度原则**：一步 = 一次可验证的行动

**今日金句**：ReAct 靠直觉走路，Planner 先画地图；地图会过时，所以要带 Replan 这块橡皮。
