# Day10 - Agent服务化与可观测

## 今日目标

Agent 在脚本里跑通只是第一步。要让别人用上，需要把它**包装成服务**（API）；要让它出了问题能查，需要**可观测性**（Observability）。

学完今天，你将能够：

1. 把 Agent 包装成 HTTP API 服务（含同步与异步任务两种模式）
2. 设计 Agent 的日志规范：轨迹日志（Trajectory Log）
3. 用 Trace ID 追踪一次请求的完整链路（跨多个工具/子 Agent）
4. 采集核心指标：延迟、成功率、Token 消耗、成本
5. 设置告警规则：错误率突增、成本超限、P99 延迟

---

## 一、为什么 Agent 需要服务化

### 1.1 脚本 vs 服务

| 维度 | 脚本（本地跑） | 服务（对外提供） |
|------|--------------|----------------|
| 触发方式 | 手动执行 | API 调用 / 事件触发 |
| 并发 | 单次一个 | 多请求同时处理 |
| 状态 | 进程内存，退出即失 | 持久化，可恢复 |
| 监控 | print 到控制台 | 结构化日志 + 指标 + 告警 |
| 失败处理 | 崩了重跑 | 重试、降级、熔断 |

### 1.2 同步 vs 异步 API

Agent 任务往往耗时几十秒到几分钟，不适合阻塞式 HTTP：

- **同步 API**：适合短任务（< 10s），请求-响应一次完成
- **异步 API**：适合长任务——提交后立即返回 task_id，客户端轮询或接收回调

```
POST /tasks            -> {"task_id": "T-123", "status": "running"}
GET  /tasks/T-123      -> {"status": "running", "progress": "3/5"}
GET  /tasks/T-123      -> {"status": "done", "result": "..."}
```

### 1.3 服务分层

```
API 网关（鉴权/限流/路由）
    │
    ▼
Agent 服务层（编排执行）
    │
    ├── 工具层（搜索/数据库/文件）
    ├── 记忆层（会话/长期）
    └── 模型层（LLM 调用）
```

对应代码：`Code/01_fastapi_service.py`（用标准库模拟，无需安装 FastAPI 也能跑）

## 二、轨迹日志（Trajectory Log）

### 2.1 普通日志不够用

普通 Web 日志记录"请求进、响应出"。但 Agent 一次请求内部有**多轮循环**：思考 → 调工具 → 观察 → 再思考……

如果只记录输入输出，出了问题根本不知道中间哪一步错了。

### 2.2 轨迹日志要记录什么

每一次 Agent 循环至少记录：

```
{
  "trace_id": "tr-abc123",       # 一次请求的唯一标识
  "step": 3,                     # 第几轮循环
  "thought": "需要先查库存",      # 思考内容
  "action": "query_inventory",  # 调用的工具
  "params": {"sku": "A100"},    # 工具参数
  "observation": "库存 42 件",    # 工具返回
  "tokens_used": 850,           # 本步消耗
  "duration_ms": 1200           # 本步耗时
}
```

### 2.3 三个日志层次

| 层次 | 内容 | 用途 |
|------|------|------|
| **请求级** | trace_id、用户、输入、最终输出、总耗时 | 排障入口 |
| **步骤级** | 每轮循环的思考/行动/观察 | 定位失败步骤 |
| **依赖级** | LLM 调用、外部工具的原始请求响应 | 深挖根因 |

对应代码：`Code/02_trajectory_log.py`

## 三、链路追踪（Distributed Tracing）

### 3.1 Trace ID 贯穿始终

一次用户请求可能触发：主 Agent → 3 个工具 → 1 个子 Agent → 2 个 LLM 调用。

所有这些环节都要带上**同一个 trace_id**，才能串成完整链路：

```
trace_id: tr-001
├── span: main_agent (1200ms)
│   ├── span: llm_call_1 (300ms)     思考
│   ├── span: tool_search (400ms)    搜索工具
│   ├── span: tool_db (250ms)        数据库工具
│   └── span: sub_agent (180ms)      子 Agent
│       └── span: llm_call_2 (150ms)
└── span: output_guard (50ms)
```

### 3.2 Span 的关键字段

- `trace_id`：整条链路唯一
- `span_id`：单个环节唯一
- `parent_span_id`：父环节（构成树）
- `name / status / duration`：基础属性

这是 OpenTelemetry 等标准追踪体系的核心概念。生产中接入 OTel 即可把 Agent 链路送进 Jaeger / Tempo。

### 3.3 追踪能回答的问题

- 这次请求慢在哪？（看最长 span）
- 为什么调了 5 次工具才完成？（看步骤序列）
- 子 Agent 的失败有没有拖垮主流程？（看 status）

对应代码：`Code/03_tracing.py`

## 四、指标与告警（Metrics & Alerting）

### 4.1 Agent 核心指标

**质量指标**

| 指标 | 定义 | 意义 |
|------|------|------|
| 任务成功率 | 成功任务数 / 总任务数 | 最重要的健康度 |
| 工具选对率 | 正确工具调用次数 / 总调用 | 衡量"大脑"是否靠谱 |
| 循环轮次 | 完成任务平均需要几轮 | 越多说明规划越差 |

**性能指标**

| 指标 | 定义 |
|------|------|
| P50 / P99 延迟 | 一半 / 99% 的请求在多少毫秒内完成 |
| 首字节时间 | 用户多久看到第一个字（流式场景） |

**成本指标**

| 指标 | 定义 |
|------|------|
| Token 消耗 | 每任务平均 tokens（输入+输出） |
| 单任务成本 | Token 单价 × 消耗 + 工具调用费 |

### 4.2 告警规则设计

```
错误率 > 10%（5 分钟窗口）      → P0 立即处理
P99 延迟 > 30s                  → P1 性能劣化
单任务成本 > 上周均值 2 倍       → P1 成本异常
Token 消耗速率超预算 80%        → P2 提前预警
```

告警要避免两个极端：**报得太多没人看**（狼来了），**报得太少发现晚**。

### 4.3 指标聚合方式

- **计数器（Counter）**：只增不减——请求数、失败数
- **直方图（Histogram）**：按桶统计分布——延迟分布
- **仪表盘（Gauge）**：当前瞬时值——队列长度、进行中任务数

对应代码：`Code/04_metrics_alert.py`

## 五、今日核心要点

```
1. Agent 服务化的关键选型：短任务同步 API，长任务异步 task_id 轮询
2. 轨迹日志 = 请求级 + 步骤级 + 依赖级，三层缺一不可
3. trace_id 贯穿主 Agent、工具、子 Agent，span 树还原完整链路
4. 核心指标三类：质量（成功率）、性能（P99 延迟）、成本（Token/费用）
5. 告警要有分级（P0/P1/P2），阈值参考历史基线而非拍脑袋
6. 可观测的目的：从"猜 Agent 在干什么"变成"看见 Agent 在干什么"
```

## 七、延伸思考

1. 流式输出（SSE/WebSocket）对服务化设计有什么额外要求？
