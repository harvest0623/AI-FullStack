## 二、为什么需要多 Agent

| 动机 | 说明 | 例子 |
|------|------|------|
| **上下文隔离** | 单 Agent 上下文装不下长任务，各干各的互不污染 | 研究员检索文献 vs 写手写作 |
| **专业性** | 不同角色不同系统提示与工具集 | 客服 Agent（沟通工具）vs 分析 Agent（数据工具） |
| **并行** | 无依赖的子任务同时跑 | 三个区域的分析各自并行 |
| **对抗与制衡** | 互相审查，降低单点偏差 | 正方/反方辩论 + 裁判 |

> **反直觉但重要**：多 Agent 不是"更强"，而是"更省上下文、更专注"。能单 Agent 解决的，别上多 Agent——每多一个 Agent 就多一份协调成本。

## 三、四种协作模式

### 3.1 Supervisor（主从编排）

```
                 ┌──────────────┐
      任务 ────▶ │  Supervisor   │  分派/汇总，不干具体活
                 └──┬────┬────┬──┘
            ┌──────┘    │    └──────┐
            ▼           ▼           ▼
        ┌───────┐  ┌───────┐  ┌───────┐
        │Worker │  │Worker │  │Worker │  各有一技之长
        │ 数据  │  │ 写作  │  │ 审查  │
        └───────┘  └───────┘  └───────┘
```
- **结构**：一个主 Agent 做路由与聚合，多个专职 Agent 做事
- **适用**：任务可分解为"路由 → 执行 → 汇总"的场景
- **要点**：Supervisor 的 Prompt 决定路由质量；Worker 之间不直接通信

### 3.2 Pipeline（流水线）

```
任务 → [分析] → [写作] → [审查] → 定稿
        产出     输入    产出
```
- **结构**：串行，上一步产出是下一步输入
- **适用**：阶段式加工（研究→写作→审校）
- **要点**：接口要约定好（阶段间传什么结构）；一段失败整条线要处理

### 3.3 Debate（辩论收敛）

```
 问题 ─▶ 正方立论 ─▶ 反方驳斥 ─▶ 正方修正 ─▶ …（N轮）─▶ 裁判总结
```
- **结构**：对立观点互相攻击，裁判收敛
- **适用**：质量敏感的判断类任务（方案评审/风险识别）
- **要点**：轮数 2-3 轮足够；裁判只看论点不看面子

### 3.4 GroupChat（群聊调度）

```
 场景：多角色围绕目标自由发言
 调度：主持人决定下一个该谁说话（基于相关性/轮转）
 终止：主持人宣布结论 or 达到轮次上限
```
- **结构**：N 个角色 + 1 个调度者，发言顺序动态决定
- **适用**：开放式讨论（头脑风暴/方案共创）
- **要点**：没有调度的群聊=灾难（抢话/跑题/不收敛），**调度者是多 Agent 的灵魂**

## 四、Handoff 与共享状态

**Handoff（移交）**：Agent A 认为任务该 B 处理，传递"目标 + 已有上下文摘要"：

```
A（客服）：这个问题需要技术支持 → handoff(技术Agent, 摘要=用户问题+已试步骤)
B（技术）：接收完整上下文继续处理
```

**共享状态（黑板模式）**：所有 Agent 读写同一块"黑板"：

```
blackboard = {
    "goal": ...,
    "findings": [...],      # 谁查到什么写上去
    "todo": [...],
    "decisions": [...],
}
```

| 方式 | 优点 | 缺点 |
|------|------|------|
| 消息传递（Handoff） | 松耦合，职责清晰 | 上下文重复传递，信息可能失真 |
| 共享黑板 | 信息零重复，全局一致 | 并发写冲突，需要锁/版本 |

## 五、成本与复杂度警示

| 问题 | 表现 | 对策 |
|------|------|------|
| **token 爆炸** | 每个 Agent 都带系统提示+历史 | 角色提示精简；传递摘要不传全史 |
| **错误传播** | 上游 Agent 错，下游照单全收 | 阶段校验（Day07 轨迹检查） |
| **无限讨论** | 群聊不收敛 | 轮次上限 + 调度者判终止 |
| **调试地狱** | 4 个 Agent 的轨迹交织 | 统一 trace_id，按 Agent 分流日志（Day10） |

> **设计红线**：从单 Agent 起步，出现"上下文挤爆"或"角色工具冲突"时再拆分。多 Agent 是解药不是补药。

## 九、小结

- **四个动机**：上下文隔离、专业性、并行、制衡——先问动机再上多 Agent
- **四种模式**：Supervisor（路由聚合）、Pipeline（串行加工）、Debate（对抗收敛）、GroupChat（调度讨论）
- **两种协作机制**：Handoff（移交带摘要）与黑板（共享状态）
- **复杂度警示**：token 爆炸、错误传播、无限讨论、调试地狱——调度者是灵魂，上限是缰绳

**今日金句**：多 Agent 不是加人手，是拆上下文；没有调度者的群聊不是协作，是灾难。
