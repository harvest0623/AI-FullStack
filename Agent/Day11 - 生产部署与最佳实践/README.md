# Day11 - 生产部署与最佳实践

## 今日目标

Agent 从 Demo 到生产之间隔着一条鸿沟：Demo 跑通只是 20%，剩下的 80% 是部署、版本、成本、回滚这些"工程脏活"。今天把这些一次性讲清楚。

学完今天，你将能够：

1. 执行灰度发布：新版本 Agent 如何安全地铺开流量
2. 管理 Prompt 版本：把 Prompt 当代码管理（这可能是最重要的实践）
3. 制定回滚策略：出问题后 1 分钟内恢复
4. 优化成本：缓存、模型分级、上下文压缩
5. 使用 PoC -> 生产检查清单，避免遗漏关键项

## 一、灰度发布（Canary Release）

### 1.1 为什么不能直接全量上线

Agent 的行为由 LLM 决定，而 LLM 是**概率性的**：新 Prompt 在 100 个测试用例上全过，也可能在生产第 101 个真实请求上翻车。灰度发布用真实流量小规模验证。

### 1.2 灰度流程

```
新版本 v2 发布
    │
    ├─ 5% 流量 -> v2（观察：成功率/延迟/成本）
    │    │
    │  正常 ──> 20% -> 50% -> 100%（每步观察一段时间）
    │  异常 ──> 立即回滚到 v1（流量切回，用户几乎无感）
    │
    └─ 95% 流量继续走 v1（稳定版兜底）
```

### 1.3 灰度期间的观察指标

- **成功率**：v2 与 v1 对比，下降超过 2 个百分点即告警
- **成本**：新 Prompt 经常更长，Token 消耗可能悄悄翻倍
- **用户反馈**：点赞/点踩、转人工率（Agent 失败的代理信号）

### 1.4 流量切分的维度

| 维度 | 示例 | 适用 |
|------|------|------|
| 随机百分比 | 5% 用户 | 通用 |
| 白名单 | 先给内部员工用 | 信任优先 |
| 按用户特征 | 只对新用户开放 | 特性验证 |

对应代码：`Code/01_canary_release.py`

## 二、Prompt 版本管理

### 2.1 Prompt 就是代码

一段 Prompt 的改动，效果可能天差地别——它就是 Agent 的"源代码"，必须像代码一样管理：

- **版本化存储**：每次修改有版本号、作者、时间、改动说明
- **变更评审**：改动前跑回归测试集（Day07 的评估集）
- **可追溯**：线上问题能定位到具体 Prompt 版本
- **可回滚**：一键切回上一版

### 2.2 版本策略

```
main（生产）
  ├── v1.2.0（当前生产）
  ├── v1.3.0-rc1（灰度中）
  └── v1.4.0-dev（开发中）

语义化版本：
  主版本：架构级改动（如换 ReAct 为 Plan-Execute）
  次版本：新增工具/能力
  修订号：措辞微调、bug 修复
```

### 2.3 A/B 测试：用数据选 Prompt

两个候选 Prompt 谁更好？不要靠感觉，用同一评估集对比：

```
Prompt A：成功率 82%，平均 3200 tokens
Prompt B：成功率 87%，平均 4100 tokens
```

决策：如果成功率差价带来的收益 > Token 成本差，选 B；否则选 A。**把 Prompt 选型变成 ROI 计算。**

对应代码：`Code/02_prompt_versioning.py`

## 三、回滚策略

### 3.1 回滚的触发条件

| 信号 | 阈值示例 | 动作 |
|------|---------|------|
| 成功率下跌 | < 90%（基线 95%） | 自动回滚 |
| P99 延迟 | > 30s 持续 5 分钟 | 自动回滚 |
| 成本突增 | 单任务成本 > 2 倍基线 | 告警+人工决策 |
| 用户投诉 | 集中出现 | 人工回滚 |

### 3.2 回滚的三层资源

回滚不只是切回旧代码，要同时考虑：

1. **代码/Prompt 回滚**：流量切回 v1
2. **数据兼容**：v2 写入的新格式数据，v1 能否读取？
3. **状态迁移**：v2 创建的进行中任务如何处理？（通常让它们跑完）

### 3.3 回滚演练

回滚方案必须**定期演练**（如每月一次），否则关键时刻一定掉链子。演练检查：

- 切换耗时是否 < 1 分钟
- 切换过程是否有用户报错
- 切换后监控指标是否恢复正常

对应代码：`Code/03_rollback.py`

## 四、成本优化

### 4.1 成本构成

```
总成本 = LLM Token 费 + 工具调用费（搜索 API 等）+ 基础设施（服务器/向量库）
```

其中 LLM Token 通常占 60% 以上，是优化重点。

### 4.2 优化手段一：缓存

| 缓存类型 | 命中条件 | 效果 |
|---------|---------|------|
| **精确缓存** | 完全相同的输入 | 直接返回，0 成本 |
| **语义缓存** | 语义相同的不同表述 | 命中率更高（用向量相似度判断） |

语义缓存是 Agent 特有的优化：用户问"今天多少度"和"今日气温如何"，答案可以复用。

### 4.3 优化手段二：模型分级

不是每一步都需要最强的模型：

```
任务路由：
  简单任务（格式转换、分类）  -> 小模型（成本 1/10）
  常规任务（问答、摘要）     -> 中档模型
  复杂任务（多步推理、代码）  -> 旗舰模型
```

一个真实数字感受：旗舰模型 $15/百万 token，小模型 $0.5/百万 token，**分级路由能省 70%+ 成本**。

### 4.4 优化手段三：上下文压缩

长对话的记忆塞满上下文，Token 消耗线性膨胀：

- 保留最近 N 轮完整对话
- 更早的对话压缩成摘要
- 工具返回的大结果只存关键字段

对应代码：`Code/04_cost_optimization.py`

## 五、PoC -> 生产检查清单

```
功能与质量
  [ ] 核心场景成功率 > 预期基线（如 85%）
  [ ] 评估集覆盖边界情况（空输入/超长输入/对抗输入）
  [ ] 失败时有兜底话术，不会对用户裸抛异常

安全与合规
  [ ] 三层护栏上线（输入/行为/输出）
  [ ] 高危操作有审批门
  [ ] 敏感数据脱敏 + 日志合规审查
  [ ] Prompt 注入测试通过

服务与稳定性
  [ ] 超时与重试策略生效（LLM/工具）
  [ ] 限流与熔断配置
  [ ] 灰度发布方案就绪
  [ ] 回滚演练通过（<1 分钟切换）

可观测
  [ ] 轨迹日志与链路追踪接入
  [ ] 核心指标看板（成功率/P99/成本）
  [ ] 告警规则配置并验证过会响

成本
  [ ] 单任务成本基线建立
  [ ] 缓存与模型分级已评估
  [ ] 预算熔断上线（防跑飞）
```

## 六、今日核心要点

```
1. LLM 是概率系统，新版本必须灰度：5% -> 20% -> 50% -> 100%
2. Prompt 就是代码：版本化、评审、可回滚，改动跑回归评估
3. Prompt 选型不靠感觉靠 A/B：成功率与成本的 ROI 权衡
4. 回滚三层：代码切回 + 数据兼容 + 存量任务处理，且要演练
5. 成本三板斧：语义缓存、模型分级路由、上下文压缩
6. 上线前过检查清单：质量/安全/稳定/可观测/成本五组缺一不可
```

## 八、延伸思考

1. 灰度观察期设多长合适？太短了看不出长尾问题，太长了发布太慢。
