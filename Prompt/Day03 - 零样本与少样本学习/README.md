# Day03 - 零样本与少样本学习

零样本（Zero-Shot）和少样本（Few-Shot）是 Prompt 工程最核心的两项技术，决定了 LLM 在没有微调的情况下能否胜任特定任务。零样本直接下达指令，依赖模型预训练知识；少样本则提供少量"输入→输出"示例，让模型通过上下文学习（In-Context Learning）归纳出模式。本章围绕 SmartCS 智能客服场景，对比零样本与少样本的适用边界，讲解示例选择策略（数量、顺序、多样性、代表性）与四大常见模式（分类、抽取、转换、生成），并厘清 Few-Shot 与微调的本质区别，帮助你用最低成本让 LLM 听懂"业务语言"。

## 学习目标

- 掌握零样本（Zero-Shot）的定义、原理、适用场景与局限性
- 掌握少样本（Few-Shot）的定义、原理（In-Context Learning）与对输出的影响
- 理解 One-Shot（单样本）的定位与作用
- 掌握 Few-Shot 示例选择策略：数量、顺序、多样性、代表性、一致性
- 能编写标准 Few-Shot 格式的 Prompt
- 理解 Few-Shot 与微调（Fine-tuning）的本质区别与选型依据
- 理解示例偏差对输出的影响
- 掌握 Few-Shot 四大常见模式：分类 / 抽取 / 转换 / 生成
- 能处理边界情况（"以上都不是"选项、边缘案例、不确定规则）

## 理论知识讲解

### 1. 零样本（Zero-Shot）

#### 定义
不给任何示例，直接让 LLM 执行任务。

#### 原理
依赖 LLM 在海量预训练数据中已学到的知识与能力。模型凭借对指令本身的理解完成任务，无需额外示例"教"它怎么做。

#### 适用场景
- 通用知识任务（常识问答、通用翻译）
- 简单分类（情感正/负）
- 基础翻译（中英互译）
- 常见问答（通用 FAQ）

#### 零样本优势
- Prompt 简洁，token 消耗少
- 通用性强，不绑定特定示例
- 编写快，适合快速验证

#### 零样本局限
- 复杂任务表现不稳定
- 格式控制能力弱（输出格式常与预期不符）
- 特定领域任务（专业术语、自定义分类）效果差

#### 零样本增强技巧
角色设定 + 明确指令 + 输出格式约束三件套：
```
你是一位资深情感分析专家（角色）。请判断以下文本的情感倾向，输出"正面/负面/中性"（指令+格式）。
文本：{{text}}
```

### 2. 少样本（Few-Shot）

#### 定义
在 Prompt 中提供少量"输入→输出"示例，让 LLM 从中归纳模式后再处理实际输入。

#### 原理：In-Context Learning（上下文学习）
LLM 并未更新权重，而是在推理时从 Prompt 中的示例归纳出"输入到输出的映射模式"，并将该模式套用到新输入上。这是 GPT-3 论文揭示的核心能力。

#### Few-Shot 如何影响输出
- **格式模仿**：示例的输出格式会被复制到新输出
- **风格对齐**：示例的语气、用词风格会被模仿
- **模式归纳**：示例展示的判断逻辑会被泛化

#### 示例数量
通常 1-5 个，并非越多越好。示例过多会：增加 token 成本、稀释关键信息、可能引入噪声。

#### 适用场景
- 分类任务（情感、意图）
- 格式化输出（固定 JSON 结构）
- 风格迁移（模仿特定写作风格）
- 特定领域任务（自定义业务分类）

### 3. One-Shot（单样本）

介于零样本和少样本之间，只给一个示例。一个示例的主要作用是**示范格式**，让模型知道"输出长什么样"。

```
示例：
输入：这个耳机太棒了
输出：{"sentiment": "正面"}

输入：用了一周就坏了
输出：
```

### 4. Few-Shot 示例选择策略

#### 数量
- 1-3 个通常够用
- 复杂任务可加到 5 个
- 超过 5 个边际收益递减，成本却线性增长

#### 顺序
影响输出（首尾位置效应）。把与当前输入最相似的示例放在最后（近因效应），效果更好。

#### 多样性
覆盖不同类别 / 边缘情况，避免示例全是同一类导致模型偏向。

#### 代表性
选择典型代表而非特殊案例。特殊案例可能误导模型归纳出错误模式。

#### 一致性
示例格式必须统一。格式不一致 → 输出格式混乱。

#### 示例质量 > 数量
一个高质量示例胜过五个低质量示例。示例中的错误会被模型复制。

### 5. Few-Shot 标准格式

```
输入：[示例输入1]
输出：[示例输出1]

输入：[示例输入2]
输出：[示例输出2]

输入：{{实际输入}}
输出：
```

也可用 `Q:` / `A:` 或 XML 标签等格式，关键是**示例之间格式统一**。

### 6. Few-Shot 与微调（Fine-tuning）的区别

| 维度 | Few-Shot | Fine-tuning |
|------|---------|-------------|
| 是否更新权重 | 否（In-Context Learning） | 是（更新模型权重） |
| 推理时是否需示例 | 需要，每次都带 | 不需要 |
| 训练成本 | 无需训练，即用即写 | 需训练数据与算力 |
| 适应性 | 任务变化时改 Prompt 即可 | 需重新训练 |
| 数据量需求 | 1-5 个示例 | 通常数百条起 |
| 性能上限 | 中高 | 高（极致性能） |
| 推理成本 | 高（每次带示例） | 低（不带示例） |

**何时用 Few-Shot**：快速验证、任务变化频繁、数据量少、需快速迭代
**何时用 Fine-tuning**：固定任务、大量数据、追求极致性能、推理成本敏感

### 7. 示例偏差对输出的影响

- **示例全正面** → LLM 倾向输出正面（类别偏差）
- **示例格式不一致** → 输出格式混乱
- **示例中有错误** → LLM 可能复制错误
- **示例全是简单案例** → 遇到复杂输入表现差

### 8. Few-Shot 常见模式

| 模式 | 输入 → 输出 | SmartCS 应用 |
|------|------------|-------------|
| 分类模式 | 文本 → 类别 | 客服工单分类 |
| 抽取模式 | 文本 → 结构化信息 | 从消息提取订单信息 |
| 转换模式 | A 格式 → B 格式 | 用户消息转 JSON |
| 生成模式 | 描述 → 内容 | 根据工单生成回复话术 |

### 9. 边界情况处理

- **添加"以上都不是"选项**：当输入不属于任何已知类别时，避免模型硬凑
- **在示例中包含边缘案例**：教模型识别边界情况
- **明确处理不确定情况的规则**：如"若无法判断，输出 unknown"

```
示例（含边界）：
输入：今天天气真好
输出：{"intent": "other", "note": "非售后话题"}

输入：{{user_message}}
输出：
```

## 关键知识点总结

### Zero-Shot vs Few-Shot vs Fine-tuning 对比表

| 维度 | Zero-Shot | Few-Shot | Fine-tuning |
|------|-----------|---------|-------------|
| 示例数 | 0 | 1-5 | 数百-数万 |
| 更新权重 | 否 | 否 | 是 |
| 推理带示例 | 否 | 是 | 否 |
| 编写成本 | 低 | 中 | 高 |
| 格式控制 | 弱 | 强 | 强 |
| 适用 | 简单通用任务 | 分类/格式/领域 | 固定任务/极致性能 |

### 示例选择策略速查

| 策略 | 要点 |
|------|------|
| 数量 | 1-3 够用，最多 5 |
| 顺序 | 相似示例放最后 |
| 多样性 | 覆盖各类别与边缘 |
| 代表性 | 选典型不选特殊 |
| 一致性 | 格式必须统一 |
| 质量 | 质量 > 数量 |

### Few-Shot 格式速查

```
输入：[示例1输入]
输出：[示例1输出]

输入：[示例2输入]
输出：[示例2输出]

输入：{{实际输入}}
输出：
```

### 常见模式速查表

| 模式 | 输入→输出 | 典型应用 |
|------|----------|---------|
| 分类 | 文本→类别 | 工单分类 |
| 抽取 | 文本→结构化 | 订单信息提取 |
| 转换 | A格式→B格式 | 消息转JSON |
| 生成 | 描述→内容 | 回复话术生成 |

## 实战练习

### 练习 1：零样本 vs 少样本对比

针对 SmartCS 意图识别任务，分别编写零样本与少样本（3 个示例）Prompt，用 10 条测试输入对比两者的准确率与格式一致性，记录差异。

### 练习 2：示例质量诊断

下面一组 Few-Shot 示例存在 3 个质量问题，请找出并修正：
```
输入：耳机很好用
输出：正面

输入：耳机有杂音
分类：负面

输入：这款耳机音质不错但续航短
输出：中性偏正面吧
```
提示：从格式一致性、输出明确性、类别偏差角度分析。

### 练习 3：边界情况设计

为 SmartCS 意图分类（faq / refund / complaint / order_query）设计一个含"以上都不是"选项的 Few-Shot Prompt，要求示例中包含至少 1 个非售后话题的边缘案例，并在真实 LLM 中测试它能否正确分类"今天上海天气怎么样"为 other。
