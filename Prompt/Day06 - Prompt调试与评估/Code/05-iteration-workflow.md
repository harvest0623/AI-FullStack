# 迭代优化流程指南

完整的 Prompt 迭代工作流文档，涵盖"诊断→假设→修改→验证→记录"的全流程，配套变更日志模板，并附一个从 v1.0 到 v2.0 的 SmartCS 客服意图识别 Prompt 完整迭代案例。

---

## 一、迭代优化五步流程

```
   ┌──────────┐
   │  诊断     │ 分析问题根因，定位是 Prompt 哪部分导致
   └────┬─────┘
        ▼
   ┌──────────┐
   │  假设     │ 提出修改方案，预测修改后效果
   └────┬─────┘
        ▼
   ┌──────────┐
   │  修改     │ 调整 Prompt，记录具体改动
   └────┬─────┘
        ▼
   ┌──────────┐
   │  验证     │ 运行测试用例，对比修改前后效果
   └────┬─────┘
        ▼
   ┌──────────┐
   │  记录     │ 保存变更日志，标注回滚方案
   └──────────┘
```

### 步骤详解

#### 1. 诊断

- 收集失败案例（来自线上日志 / 人工测试 / 用户反馈）
- 用最小化复现法找到触发问题的最少输入
- 用二分法定位是 Prompt 哪段指令 / 哪个示例导致问题
- 明确问题归类（幻觉 / 格式错 / 逻辑错 / 安全 / 一致性）

#### 2. 假设

- 基于诊断结果提出修改方案
- 预测修改后会带来的效果（解决什么问题、可能引入什么副作用）
- 设计验证用例（包括正向验证 + 回归验证）

#### 3. 修改

- 仅修改与问题直接相关的部分，不做无关改动
- 保留原版 Prompt 备份，便于回滚
- 记录具体改动内容（改了哪句话、加了哪个示例、调了哪个参数）

#### 4. 验证

- 运行全部测试用例（包括失败用例 + 原有通过用例）
- 用 A/B 测试对比修改前后效果
- 确保修改解决了问题且未引入新问题（回归测试）

#### 5. 记录

- 在变更日志中记录：版本号、日期、修改内容、修改原因、测试结果、回滚方案
- 将新失败案例补充到测试集
- 若修改未达预期，回滚到上一稳定版本并重新诊断

## 三、完整迭代案例：SmartCS 意图识别 Prompt 从 v1.0 到 v2.0

### 背景

SmartCS 客服系统的意图识别 Prompt 用于将用户输入分类为 5 类：FAQ咨询 / 订单查询 / 退换货 / 投诉 / 闲聊。上线后收集到一系列失败案例，需要迭代优化。

---

### v1.0 - 初始版本

#### Prompt

```
你是 SmartCS 意图识别系统。
判断用户输入属于哪个意图：FAQ咨询 / 订单查询 / 退换货 / 投诉 / 闲聊
用户输入：{{user_message}}
输出 JSON：{"intent": "...", "confidence": 0.0~1.0}
```

### v1.1 - 增加 Few-Shot 示例

#### 诊断

- F-001/F-003：模型未学会识别"带情绪的咨询"应判投诉
- F-002：单标签设计局限，需支持多标签
- F-004：中英混合输入识别能力不足
- F-005：缺少"仅输出 JSON"的强约束

#### 假设

- 增加 3 个 Few-Shot 示例覆盖：带情绪的咨询、多意图、中英混合
- 改为多标签输出
- 强化 JSON 格式约束

#### 修改

#### Prompt

```
你是 SmartCS 意图识别系统。
判断用户输入属于哪些意图（可多选）：FAQ咨询 / 订单查询 / 退换货 / 投诉 / 闲聊

示例 1：
输入：我那个订单 #20240518 怎么还没到啊，都 5 天了！
输出：{"intents": ["投诉", "订单查询"], "confidence": 0.9, "reason": "用户查询订单但带有强烈不满情绪"}

示例 2：
我想退那个吹风机，顺便问下退款多久到账
输出：{"intents": ["退换货", "FAQ咨询"], "confidence": 0.85, "reason": "主诉求退货，附带询问退款到账时间"}

示例 3：
你们这破服务，等了 3 天没人理
输出：{"intents": ["投诉"], "confidence": 0.95, "reason": "纯投诉，未涉及具体业务查询"}

用户输入：{{user_message}}
仅输出 JSON，不要任何其他文本：
{"intents": [...], "confidence": 0.0~1.0, "reason": "..."}
```

### v2.0 - 增加中英混合处理与置信度阈值

#### 诊断

- v1.1 后剩余问题：F-004 中英混合输入仍被判为闲聊
- 新收集失败案例：部分模糊输入置信度过高（0.9+），应触发人工复核

#### 假设

- 在 Prompt 中明确说明"支持中英混合输入识别"
- 增加中英混合示例
- 增加置信度阈值规则：< 0.7 时标记需人工复核

## 四、迭代最佳实践

1. **小步快跑**：每次迭代只解决 1-2 类问题，避免大改动引入不可控风险
2. **回归优先**：每次修改后先跑回归测试，确保未引入退化，再验证新改进
3. **版本备份**：每个版本独立存档，标注版本号，便于回滚
4. **失败案例库**：持续收集失败案例，形成测试集，每个版本都用此集回归
5. **灰度发布**：新版本先灰度 10% 流量，观察线上指标 24-48 小时后再全量
6. **定期复盘**：每月复盘迭代记录，分析哪些修改有效、哪些无效，沉淀经验
7. **团队协作**：Prompt 修改需经过 Code Review 流程，至少 1 人审核
8. **避免过度优化**：当准确率提升边际递减时，考虑从模型升级、RAG 补充知识等其他维度突破，而非无限调 Prompt
