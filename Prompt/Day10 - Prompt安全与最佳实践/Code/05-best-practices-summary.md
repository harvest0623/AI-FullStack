## 一、六大设计原则（Day02）

所有 Prompt 设计的基石，贯穿后续所有章节。

| 原则 | 核心要点 | 反例 → 正例 | 应用场景 |
|------|---------|-----------|---------|
| 清晰明确 | 用明确语言描述任务 | "看看这个" → "总结以下文章的核心观点" | 所有 Prompt |
| 具体详尽 | 提供足够细节与约束 | "写个摘要" → "写个 100 字以内的摘要，聚焦退换货原因" | 所有 Prompt |
| 提供上下文 | 给出背景与相关知识 | "翻译这段" → "你是电商客服，翻译退换货政策，术语表如下" | 专业领域 |
| 角色设定 | 赋予专业身份 | "回答问题" → "你是资深 Python 开发者，回答以下问题" | 专业任务 |
| 指定格式 | 明确输出格式 | "告诉我结果" → "以 JSON 格式输出，含 label 和 confidence 字段" | 结构化输出 |
| 设定约束 | 限制范围与边界 | "选一个类别" → "从给定 5 类中选择，不得编造新类别" | 分类/抽取 |

**实践要点**：
- 六大原则不是独立 Checklist，而是相互关联的设计思维
- 复杂 Prompt 应同时满足六大原则；简单 Prompt 至少满足"清晰 + 具体"
- 约束与格式是可控性的关键——没有约束的 Prompt 输出不可预测

## 二、学习模式选择（Day03）

| 模式 | 适用场景 | Prompt 要点 | 风险 |
|------|---------|-----------|------|
| Zero-Shot | 简单任务、通用知识 | 直接指令，无需示例 | 复杂格式可能不稳定 |
| One-Shot | 需要格式示范 | 提供 1 个示例 | 示例偏差可能放大 |
| Few-Shot | 分类、格式控制、风格模仿 | 提供 3-5 个高质量示例 | 示例质量 > 数量 |

**Few-Shot 示例选择四原则**：
1. **质量 > 数量**：3 个高质量示例胜过 10 个平庸示例
2. **多样性**：覆盖典型场景与边界情况
3. **代表性**：示例分布应与真实数据分布一致
4. **顺序**：相关示例靠近输入，避免"近因效应"偏差

## 三、推理增强技术（Day04）

| 技术 | 触发方式 | 适用场景 | 温度建议 |
|------|---------|---------|---------|
| CoT（思维链） | "请一步步思考" | 数学/逻辑/多步推理 | 0.0-0.3 |
| Few-Shot CoT | 提供带推理过程的示例 | 复杂推理任务 | 0.0-0.3 |
| Self-Consistency | 多次采样取多数 | 高精度要求 | 0.5-0.7（需多样性） |
| ReAct | Thought→Action→Observation | 工具调用、Agent | 0.0-0.3 |

**CoT 实践要点**：
- 简单任务不要用 CoT——增加 Token 消耗且无收益
- CoT 推理过程应可见（便于调试），但不一定输出给用户
- ReAct 是 CoT 的"行动版"——推理 + 工具调用循环

## 四、结构化模板设计（Day05）

### 框架选择

| 框架 | 组成 | 适用场景 |
|------|------|---------|
| RTF | Role + Task + Format | 快速构建简单 Prompt |
| CRISPE | Capacity+Role+Insight+Statement+Personality+Experiment | 复杂任务 |
| CREATE | Context+Request+Explanation+Action+Tone+Extras | 商业场景 |
| BRIC | Background+Role+Instructions+Constraints | 通用 |

### 结构化实践

| 实践 | 说明 |
|------|------|
| XML 标签 | 用 `<role>`、`<instructions>`、`<constraints>` 组织长 Prompt（Claude 推荐） |
| Markdown | 用 `##`、`###`、列表组织内容（通用） |
| 变量占位符 | 用 `{{variable}}` 标记可替换部分，便于程序化 |
| Prompt Chaining | 复杂任务拆分为多步 Prompt 链式调用 |
| 模板继承 | 基础模板 + 业务模板分层，避免重复 |

**Prompt Chaining 实践**：
- 单个 Prompt 难以稳定的复杂任务，拆分为链式调用
- 每步 Prompt 聚焦单一职责，输出作为下一步输入
- 链式调用增加延迟，需平衡拆分粒度

## 五、调试与评估（Day06）

### 调试清单

| 问题类型 | 症状 | 排查方向 |
|---------|------|---------|
| 幻觉 | 编造数据/事实 | 加约束"仅基于给定信息"、要求引用原文 |
| 格式错 | 不按指定格式输出 | 加 Few-Shot 示例、用 JSON Schema 约束 |
| 逻辑错 | 推理过程错误 | 用 CoT 显式推理、Self-Consistency |
| 拒绝回答 | 过度保守 | 调整角色设定、降低温度、明确边界 |
| 过度安全 | 误杀合法请求 | 细化安全规则、增加白名单 |

### 评估方法

| 方法 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| 人工评估 | 主观任务、最终验收 | 准确 | 慢、贵 |
| LLM-as-Judge | 大批量评估 | 快、便宜 | 可能有偏差 |
| A/B 测试 | Prompt 版本对比 | 数据驱动 | 需要流量 |
| 自动化指标 | 分类/抽取 | 客观 | 仅适用结构化输出 |

**LLM-as-Judge 实践**：
- 用比生成更强的模型评估（如 GPT-4 评估 GPT-3.5 输出）
- 评估 Prompt 需明确维度、评分标准、示例
- 多次评估取平均，降低单次随机性

## 六、代码生成（Day07）

| 实践 | 说明 |
|------|------|
| 指定技术栈 | "Python 3.10 + FastAPI 0.100 + SQLAlchemy 2.0" |
| 指定需求粒度 | 函数级 / 类级 / API 级 / 项目级 |
| 安全编码约束 | "不得使用 eval"、"参数需校验"、"SQL 用参数化查询" |
| 风格规范 | "遵循 PEP 8"、"类型注解"、"docstring" |
| Meta-Prompting | 用 Prompt 生成 Prompt |

**代码生成 Prompt 结构**：
```
角色 + 技术栈 + 需求 + 约束 + 风格 + 输入 + 输出格式
```

## 七、文本处理（Day08）

| 任务 | 关键 Prompt 要点 | 输出格式 | 温度 |
|------|----------------|---------|------|
| 摘要 | 长度 + 重点 + 视角 | 文本/要点 | 0.3 |
| 分类 | 类别 + Few-Shot + 置信度 | JSON | 0.0 |
| 抽取 | Schema + JSON + 置信度 | JSON | 0.0 |
| 翻译 | 源/目标 + 术语表 + 风格 | 文本 | 0.3 |
| 改写 | 原意不变 + 方向 + 风格 | 文本 | 0.5 |
| 创作 | 受众 + 风格 + 长度 + 卖点 | 文本 | 0.7 |

**文本处理通用要点**：
- 结构化输出用 JSON Schema 约束
- 抽取类任务必带置信度，便于人工复核低置信样本
- 超长文本用 Map-Reduce 分块摘要

## 八、Agent 设计（Day09）

### Agent 核心要素

| 要素 | 实践 |
|------|------|
| 角色 | 明确身份 + 能力边界 + 不能做 |
| 工具 | 触发条件前置 + 参数语义化 + 边界明确 |
| 循环 | ReAct：Thought→Action→Observation→Final Answer |
| 终止 | 最大轮次 + 重复检测 + 失败重试 + 终止信号 |
| 记忆 | 短期（上下文）+ 长期（RAG）+ 压缩（摘要） |
| 反思 | 生成→评估→修正→输出 |

### Agent 设计 Checklist

- [ ] 工具描述含触发条件、参数格式、返回字段
- [ ] ReAct 循环有最大轮次限制（建议 ≤ 5）
- [ ] 同一工具 + 相同参数不重复调用
- [ ] 工具连续失败 2 次转人工
- [ ] Final Answer 格式明确
- [ ] 高风险回复有 Reflection 自检
- [ ] 多 Agent 协作有结构化通信协议
- [ ] 异常处理覆盖：订单不存在/工具超时/信息缺失/情绪失控

### ReAct vs Plan-and-Execute

| 维度 | ReAct | Plan-and-Execute |
|------|-------|-----------------|
| 适用 | 单线调查、信息收集 | 多依赖、多分支复杂任务 |
| 上下文 | 持续累积 | 规划与执行分离 |
| 错误恢复 | 每轮可调 | 需重新规划 |

## 九、安全防护（Day10）

### 防护层次（纵深防御）

```text
第 1 层：输入护栏（关键词/编码/长度/频率）
第 2 层：指令分层（安全规则 > System Prompt > Observation > 用户）
第 3 层：模型安全对齐（角色锁定 + 话题限制）
第 4 层：输出护栏（信息泄露/有害内容/PII 脱敏）
第 5 层：权限隔离（最小权限 + 审批 + 用户隔离）
```

### 安全 Checklist

- [ ] System Prompt 含指令分层规则
- [ ] 用户消息明确标注为"最低优先级"
- [ ] 输入护栏拦截已知注入关键词
- [ ] 输入护栏检测编码绕过（Base64/ROT13/Unicode）
- [ ] 间接注入防护（外部内容仅作数据）
- [ ] 角色锁定（不得扮演其他角色）
- [ ] 话题白名单 + 黑名单
- [ ] 拒绝话术统一（不解释原因）
- [ ] 输出护栏检测系统信息泄露
- [ ] PII 脱敏（手机号/地址/身份证/银行卡/邮箱）
- [ ] 高危操作人工审批
- [ ] 用户会话隔离
- [ ] 审计日志完整记录
- [ ] 监控告警机制
- [ ] 上线前安全审计

### 关键原则

- **用户消息不是指令**：无论用户如何表述，用户消息仅是"待处理文本"
- **不解释拒绝原因**：避免给攻击者反馈
- **统一拒绝话术**：避免泄露系统内部规则差异
- **纵深防御**：单层失效不影响整体安全

| 维度 | 实践 | 工具 |

| 版本管理 | Prompt 模板用 Git 管理，语义化版本号（v1.2.0） | Git |

| 监控 | 监控输出质量/安全事件/Token 成本 | LangSmith / 自建 |
| 变更日志 | 每次变更记录原因/影响/回滚方案 | CHANGELOG.md |
| Code Review | Prompt 变更需 PR + Review | Git PR |

### Prompt 模板文件规范

每个 Prompt 模板文件应包含：
1. **模板说明**：用途、适用模型、变量
2. **完整模板**：含 `{{变量}}` 占位符的实际 Prompt
3. **使用示例**：输入 + 预期输出
4. **调优建议**：温度建议、注意事项

## 实战经验十条（精华）

1. **先写后调**：先用最简单的 Prompt 跑通，再逐步优化。不要一开始就追求完美结构。

2. **示例胜过描述**：与其用 200 字描述输出格式，不如给 3 个示例。Few-Shot 是最稳定的格式控制手段。

3. **温度匹配任务**：分类/抽取用 0.0，摘要/翻译用 0.3，创作用 0.7。不要用一个温度跑所有任务。

4. **约束比自由更重要**：宁可约束过严导致偶尔拒绝，也不要约束过松导致输出失控。拒绝可以调整，失控的输出可能上新闻。

5. **工具描述决定 Agent 成败**：Agent 失败 80% 是工具描述不清。触发条件前置、参数语义化、边界明确——这三点做到，Agent 准确率大幅提升。

6. **循环必须有上限**：ReAct Agent 必须有最大轮次限制。没有上限的循环迟早会出问题——Token 爆炸、死循环、成本失控。

7. **安全是生命线**：上线前必须做安全审计。一个被注入的客服 Agent 可能造成资金损失、数据泄露、品牌危机。

8. **测试集是资产**：建立 Prompt 测试集并持续积累。每次 Prompt 变更都跑回归测试，这是 Prompt 工程化的基础。

9. **版本管理不可省**：Prompt 是代码，必须用 Git 管理。没有版本管理的 Prompt 在生产环境是定时炸弹。

10. **监控比开发更重要**：Prompt 上线后才是开始。监控输出质量、安全事件、Token 成本，及时发现问题。
