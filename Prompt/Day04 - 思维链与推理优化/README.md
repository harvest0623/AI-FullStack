# Day04 - 思维链与推理优化

思维链（Chain-of-Thought, CoT）是让大语言模型像人一样"逐步思考"的关键技术。面对折扣计算、退款核算、退换货资格判断这类多步骤推理任务，直接让 LLM 给出答案往往出错率很高；而一旦引导它把推理过程显式写出来，准确率会显著提升。本章围绕智能客服助手 SmartCS 的真实场景，系统讲解 CoT 的原理、触发技巧、两种形式（Zero-Shot / Few-Shot），并扩展到自洽性（Self-Consistency）、思维树（ToT）、ReAct 推理模式等高级技巧，让你在面对复杂推理任务时知道何时用、怎么用、用得好。

---

## 学习目标

完成本章后，你应能：

1. 理解思维链的工作原理，能讲清"为什么分步思考能提升推理准确率"
2. 掌握 Zero-Shot CoT 与 Few-Shot CoT 两种形式的差异，并知道何时选用
3. 熟练运用多种 CoT 触发技巧，能根据任务特点选择最合适的措辞
4. 能够判断 CoT 适用与不适用场景，避免在简单任务上过度推理
5. 掌握 Self-Consistency、Tree-of-Thoughts、ReAct 三种高级推理模式
6. 能够设计推理过程可见 / 隐藏的 Prompt，兼顾调试与用户体验
7. 识别 CoT 的常见失败模式并知道如何修正

## 理论知识讲解

### 1. 思维链（Chain-of-Thought, CoT）

#### 1.1 什么是 CoT

思维链是一种让 LLM 在给出最终答案前，**先展示中间推理过程**的提示技术。传统 Prompt 期望 LLM 直接"输入问题→输出答案"，而 CoT 则要求"输入问题→展示推理步骤→输出答案"。

```
传统方式：  问题 ─────────────────► 答案
CoT 方式：  问题 ──► 推理步骤1 ──► 推理步骤2 ──► ... ──► 答案
```

#### 1.2 原理：中间 Token 提供"思考空间"

LLM 的输出是逐 Token 生成的，每生成一个 Token 都会作为后续生成的上下文。这意味着：

- **直接作答**：LLM 必须在极少的 Token 内完成所有推理，单步推理负担过重
- **分步推理**：中间 Token 充当"工作记忆"，把复杂推理拆成多个简单推理，每步只需做一小段推理

类比人类做数学题：心算 `17 × 24` 容易出错，但列竖式一步步算就可靠得多。CoT 就是给 LLM 一张"草稿纸"。

#### 1.3 CoT 的发现

思维链技术由 Google 团队在 2022 年论文 **"Chain-of-Thought Prompting Elicits Reasoning in Large Language Models"**（Wei et al., 2022）中正式提出。论文核心发现是：在 Few-Shot 示例中展示推理过程，能让大模型在数学、逻辑、符号推理等任务上获得大幅提升。

#### 1.4 效果：数学推理准确率大幅提升

在论文给出的 GSM8K（小学数学应用题）基准上：

| 模型 | 标准 Prompting | CoT Prompting | 提升 |
|------|---------------|---------------|------|
| PaLM-540B | 17.7% | 56.9% | +39.2% |
| GPT-3 (175B) | 17.7% | 58.1% | +40.4% |

需要注意的是，CoT 的收益与模型规模强相关——小模型上 CoT 甚至可能降低性能，只有当模型规模达到一定阈值后 CoT 才显著有效。

### 2. CoT 的两种形式

#### 2.1 Zero-Shot CoT

最简单的 CoT 形式：在任意 Prompt 末尾追加一句"让我们一步一步思考"，即可触发模型的分步推理行为，无需提供任何示例。

```
{{问题}}

让我们一步一步思考。
```

#### 2.2 Few-Shot CoT

在 Prompt 中提供若干"问题→推理过程→答案"的示例，让模型模仿示例中的推理风格。

```
示例1：
问题：...
推理：Step 1 ... Step 2 ...
答案：...

示例2：
问题：...
推理：Step 1 ... Step 2 ...
答案：...

实际问题：
问题：{{问题}}
推理：
```

#### 2.3 两者对比

| 维度 | Zero-Shot CoT | Few-Shot CoT |
|------|---------------|--------------|
| 实现难度 | 极简（加一句话） | 中等（需准备示例） |
| Token 成本 | 低 | 较高（示例占 Token） |
| 可控性 | 低（推理风格由模型决定） | 高（可指定推理风格与步骤） |
| 效果稳定性 | 中 | 高 |
| 适用场景 | 通用、快速验证 | 生产环境、对推理格式有要求 |
| 推理风格 | 自由发挥 | 可统一为"Step 1/2/3"等结构 |

**经验法则**：先用 Zero-Shot CoT 快速验证任务是否需要 CoT，确认有效后再用 Few-Shot CoT 固化推理格式以提升可控性。

---

### 3. CoT 触发技巧

不同的触发措辞会在不同任务上产生差异，以下按从简到繁排列：

| 触发措辞 | 适用场景 | 效果 |
|---------|---------|------|
| "让我们一步一步思考" / "Let's think step by step" | 通用 | 最经典、最稳定 |
| "请先分析，再给出答案" | 需要分离分析与结论 | 好 |
| "请展示你的推理过程" | 需要可解释性 | 好 |
| "Step 1: ... Step 2: ... Step 3: ..." | 需要结构化推理 | 很好（强约束） |
| "先理解问题，再分析条件，最后得出结论" | 多条件决策 | 很好 |

**对客服场景的建议**：涉及金额计算、政策判断时优先用结构化触发词（Step 1/2/3），便于后续解析与审计。

---

### 4. CoT 适用场景

#### 4.1 适用场景（推理密集型任务）

| 场景类型 | SmartCS 客服示例 |
|---------|-----------------|
| 数学计算与逻辑推理 | 折扣计算、运费计算、退款金额计算 |
| 多条件决策 | 根据退换货政策判断是否符合退换条件 |
| 因果分析 | 分析订单异常原因（为何物流停滞） |
| 规则应用 | 按退换货流程引导用户操作 |

#### 4.2 不适用场景（非推理型任务）

| 场景类型 | 说明 | CoT 反而有害的原因 |
|---------|------|-------------------|
| 简单事实问答 | "你们客服电话是多少" | 无需推理，多余步骤增加出错机会 |
| 纯格式转换 | "把这段文本转成 JSON" | 任务是转换而非推理 |
| 简单分类任务 | "判断这句话是正面还是负面" | 直接分类即可，分步反而拖慢 |
| 创意生成 | "写一段节日营销文案" | 创意需要发散，过度推理会僵化输出 |

**判断准则**：如果任务需要"算"或"推导"，用 CoT；如果只是"查"或"转换"，不用。

### 5. Self-Consistency（自洽性）

#### 5.1 原理

对同一问题用**高温度**多次采样，生成 N 条不同的 CoT 推理路径，再从 N 个答案中投票取多数，作为最终答案。

```
                    ┌─► 推理路径1 ─► 答案A ┐
同一问题 ──高温度──►├─► 推理路径2 ─► 答案B ┼─► 多数投票 ─► 最终答案
                    └─► 推理路径3 ─► 答案A ┘
```

#### 5.2 步骤

1. 将温度调高（如 0.7~1.0）
2. 对同一 Prompt 采样 N 次（通常 N=5~20）
3. 从每条推理路径中提取最终答案
4. 对 N 个答案投票，取出现次数最多的答案

#### 5.3 适用场景与成本

- **适用**：高精度数学/逻辑推理、对正确率要求极高的场景
- **成本**：Token 消耗是单次 CoT 的 N 倍，延迟也是 N 倍
- **权衡**：仅在关键决策（如大额退款核算）上启用

---

### 6. Tree-of-Thoughts（ToT，思维树）

#### 6.1 原理

将推理组织成树形结构：在每个推理节点生成多个候选分支→评估各分支的前景→选择最优分支继续推理，必要时回溯。

```
                根问题
              /   |   \
          分支1  分支2  分支3      ← 生成候选
            |     ✗     |          ← 评估（剪枝）
          分支1.1     分支3.1
            |           |
          ...         答案
```

#### 6.2 与 CoT 的区别

| 维度 | CoT（思维链） | ToT（思维树） |
|------|--------------|--------------|
| 结构 | 线性（一条链） | 树形（多分支） |
| 是否评估中间状态 | 否 | 是 |
| 是否可回溯 | 否 | 是 |
| 适合任务 | 推理步骤明确 | 需要搜索/规划/探索 |
| 成本 | 低 | 高（需多次生成+评估） |

#### 6.3 适用场景

- 搜索类问题（在多个方案中找最优）
- 规划类问题（多步规划，每步有多种选择）
- 创意探索（生成多个创意方向再筛选）

---

### 7. ReAct 推理模式（Reason + Act）

#### 7.1 模式结构

ReAct 让 LLM 在**推理（Thought）**与**行动（Action）**之间交替循环：

```
Thought（思考）：分析当前状态，决定下一步该做什么
Action（行动）：调用工具 / API / 搜索
Observation（观察）：获取工具返回的结果
Thought（思考）：基于观察继续推理
...
最终：综合所有观察给出答案
```

#### 7.2 与纯 CoT 的区别

纯 CoT 只在 LLM 内部推理，无法获取外部信息；ReAct 通过 Action 调用外部工具（如查询订单系统、搜索知识库），将外部事实注入推理链。

#### 7.3 适用场景

需要外部信息的任务，例如 SmartCS 客服场景：

```
用户："我的订单为什么还没到？"
├─ Thought：需要先查订单状态
├─ Action：调用订单查询 API
├─ Observation：订单已发货，物流停滞 3 天
├─ Thought：物流异常，需查物流详情
├─ Action：调用物流查询 API
├─ Observation：包裹在转运中心滞留
└─ 最终回复：告知用户物流异常原因及处理方案
```

---

### 8. 分步推理的 Prompt 结构

一个典型的分步推理 Prompt 模板：

```
请按以下步骤处理：
1. 分析用户请求
2. 检查相关条件
3. 应用退换货政策
4. 给出结论和建议

用户请求：{{user_request}}
退换货政策：{{policy}}
```

要点：
- 步骤顺序符合逻辑（先理解→后判断→再结论）
- 每个步骤任务单一、边界清晰
- 给 LLM 留出"展示中间结果"的空间

---

### 9. 推理过程可见性

#### 9.1 让用户看到推理过程

- **优点**：增加信任度、便于人工调试、可审计
- **适用**：客服回复需向用户解释依据时

#### 9.2 隐藏推理过程

- **优点**：输出简洁、不暴露内部规则、用户体验好
- **实现**：用 XML 标签包裹推理，只输出结论部分

```
请按以下格式输出：
<reasoning>在这里展示你的推理过程</reasoning>
<answer>只在这里给出最终给用户的回复</answer>
```

解析时只取 `<answer>` 标签内容返回给用户，`<reasoning>` 留作日志审计。

---

### 10. CoT 的局限与失败模式

| 失败模式 | 表现 | 应对 |
|---------|------|------|
| 推理看似正确但结论错误 | 步骤逻辑通顺，最终答案却错 | 用 Self-Consistency 交叉验证 |
| 过度推理 | 简单问题也长篇大论 | 在 Prompt 中加"简单问题可简短回答" |
| 推理链断裂 | 中间步骤跳太多，逻辑断层 | 用 Few-Shot CoT 示范完整步骤 |
| 对非推理任务无效甚至降低性能 | 简单分类任务加上 CoT 后变差 | 识别任务类型，非推理任务不用 CoT |

## 关键知识点总结

### CoT 触发方式速查

| 触发方式 | 写法 | 强度 | 适用 |
|---------|------|------|------|
| 最简触发 | "让我们一步一步思考" | 弱 | 通用 |
| 分析先行 | "请先分析，再给出答案" | 中 | 需分离分析与结论 |
| 显式推理 | "请展示你的推理过程" | 中 | 需可解释性 |
| 结构化步骤 | "Step 1: ... Step 2: ..." | 强 | 需统一推理格式 |
| 三段式 | "先理解问题，再分析条件，最后得出结论" | 强 | 多条件决策 |

### Zero-Shot vs Few-Shot CoT 对比

| 维度 | Zero-Shot CoT | Few-Shot CoT |
|------|---------------|--------------|
| 是否提供示例 | 否 | 是 |
| 实现成本 | 极低 | 中 |
| 可控性 | 低 | 高 |
| 推理风格一致性 | 低 | 高 |
| 适用阶段 | 快速验证 | 生产部署 |

### CoT 适用 / 不适用场景表

| 任务类型 | 是否适用 CoT | 示例 |
|---------|-------------|------|
| 数学计算 | ✅ 适用 | 退款金额、折扣计算 |
| 逻辑推理 | ✅ 适用 | 退换货资格判断 |
| 因果分析 | ✅ 适用 | 订单异常原因分析 |
| 规则应用 | ✅ 适用 | 按流程引导用户 |
| 简单事实问答 | ❌ 不适用 | 客服电话查询 |
| 格式转换 | ❌ 不适用 | 文本转 JSON |
| 简单分类 | ❌ 不适用 | 情感二分类 |
| 创意生成 | ❌ 不适用 | 营销文案撰写 |

### 推理模式对比（CoT / ToT / ReAct / Self-Consistency）

| 模式 | 结构 | 是否调用工具 | 是否多路径 | 成本 | 典型场景 |
|------|------|------------|-----------|------|---------|
| CoT | 线性链 | 否 | 否 | 低 | 数学、逻辑推理 |
| Self-Consistency | 多条线性链投票 | 否 | 是（投票） | N 倍 | 高精度推理 |
| ToT | 树形搜索 | 否 | 是（剪枝） | 高 | 搜索、规划 |
| ReAct | 推理+行动循环 | 是 | 否 | 中 | 需外部信息的任务 |

## 实战练习

### 练习 1：退换货资格判断 CoT 设计

**任务**：用户购买一件商品 12 天后申请退货，请用 Few-Shot CoT 设计一个 Prompt，根据退换货政策判断是否符合退货条件。

**要求**：
- 政策：7 天无理由退货、15 天质量问题退货
- 至少提供 2 个示例（一个符合、一个不符合）
- 推理过程用 "Step 1/2/3" 结构

### 练习 2：ReAct 客服 Agent 设计

**任务**：用户反馈"订单 #20240518 物流一直不动"，请用 ReAct 模式设计一个客服 Agent Prompt，至少包含 2 轮 Thought-Action-Observation 循环。

**要求**：
- 定义可调用的工具（订单查询、物流查询）
- 模拟 Observation 内容
- 最终给出用户回复

### 练习 3：Self-Consistency 退款核算

**任务**：用户订单原价 599 元，使用满 300 减 50 优惠券，再用 9 折会员折扣，退货时需核算退款金额。请用 Self-Consistency 模式生成 3 条推理路径并投票得出最终答案。

**要求**：
- 3 条推理路径的中间步骤可以不同
- 最终答案一致（验证自洽性）
- 写明投票结果
