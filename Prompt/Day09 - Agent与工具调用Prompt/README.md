# Day09 - Agent与工具调用Prompt

> Agent 是 LLM 从"对话工具"进化为"行动主体"的关键跃迁。掌握 Agent Prompt 设计，是构建真正可用 AI 应用的核心能力。本章系统讲解 ReAct 模式、Function Calling、多步规划、多 Agent 协作、自我反思与客服 Agent 完整案例，所有模板均可直接用于主流 LLM。

---

## 本章简介

前八天我们让 LLM 学会了"说话"——它能写代码、能摘要、能分类、能创作，但始终停留在"输入文本 → 输出文本"的单轮交互。然而真实世界的任务远比文本生成复杂：用户问"我的订单到哪了"，LLM 自己并不知道订单状态，必须**调用查询接口**才能回答；用户要"帮我处理这单退货"，LLM 必须**先查订单 → 再查政策 → 再创建工单**多步执行才能完成。

这就是 Agent 登场的时刻。**AI Agent = LLM 推理引擎 + 工具调用 + 循环控制 + 记忆管理**。LLM 不再只是"回答者"，而是"决策者"——它感知用户需求，规划行动步骤，选择合适工具，执行后观察结果，再调整策略，直到完成任务。ReAct（Reason + Act）模式是当前最主流的 Agent 范式，被 LangChain、AutoGPT、OpenAI Assistants API 等广泛采用。

本章延续 SmartCS 智能客服场景：从最基础的 ReAct 循环到完整客服 Agent 系统，覆盖工具描述、多步规划、多 Agent 协作、自我反思等 Agent Prompt 的全部核心要素。Day09 是 Prompt Engineering 从"写好一段指令"迈向"设计一个智能体"的转折点，也是为后续 LLM/RAG/Agent 板块铺路的桥梁。

## 理论知识讲解

### 1. Agent 概念

#### 什么是 AI Agent

AI Agent（智能体）是以 LLM 为推理引擎、能够**感知环境 → 做出决策 → 执行行动 → 观察结果 → 调整策略**的自主系统。与单纯对话模型不同，Agent 拥有"行动力"——它能调用外部工具、操作数据库、发送消息、触发流程，而不仅仅是生成文本。

Agent 的核心组成：

```text
┌─────────────────────────────────────────────┐
│                 AI Agent 架构                │
│                                             │
│   ┌──────────┐    ┌──────────────────┐      │
│   │  LLM 大脑 │ ←→ │   记忆系统        │      │
│   │ (推理引擎)│    │ 短期 / 长期记忆   │      │
│   └────┬─────┘    └──────────────────┘      │
│        │                                    │
│        ▼                                    │
│   ┌──────────┐    ┌──────────────────┐      │
│   │  规划器   │ →  │   工具调用层      │      │
│   │ 任务分解  │    │ API / DB / 函数  │      │
│   └──────────┘    └────────┬─────────┘      │
│                            │                │
│                            ▼                │
│                   ┌──────────────────┐      │
│                   │   环境反馈        │      │
│                   │ Observation       │      │
│                   └──────────────────┘      │
└─────────────────────────────────────────────┘
```

#### Agent vs Chatbot

| 维度 | Chatbot（聊天机器人） | Agent（智能体） |
|------|---------------------|----------------|
| 核心能力 | 对话生成 | 感知 + 决策 + 行动 |
| 信息来源 | 训练知识 + 对话上下文 | 训练知识 + 工具调用 + 实时数据 |
| 输出形式 | 文本 | 文本 + 工具调用 + 环境操作 |
| 自主性 | 被动响应 | 主动规划、多步执行 |
| 状态管理 | 单轮或简单多轮 | 长期记忆、任务状态跟踪 |
| 典型代表 | 早期 ChatGPT | AutoGPT / LangChain Agent / Assistants API |
| 客服示例 | "您可以这样查询订单..." | 调用 query_order 工具后回复"您的订单已发货..." |

#### Agent 核心能力循环

```text
理解任务 → 规划步骤 → 选择工具 → 执行行动 → 观察结果 → 调整策略 → 完成目标
   ↑                                                          │
   └──────────────────── 反馈循环 ─────────────────────────────┘
```

七个核心能力缺一不可：理解任务决定方向、规划步骤拆解复杂度、选择工具决定执行路径、执行行动产生效果、观察结果获取反馈、调整策略应对异常、完成目标输出价值。

### 2. ReAct Agent 模式（核心模式）

ReAct（Reasoning + Acting）是当前最主流的 Agent 范式，由 Yao 等人 2022 年提出。其核心思想是让 LLM 在"推理"与"行动"之间交替循环，每次行动后获取真实环境反馈，再基于反馈继续推理。

#### ReAct 三要素

| 要素 | 含义 | 输出形式 |
|------|------|---------|
| Thought（思考） | 分析当前状态，决定下一步 | 自然语言推理过程 |
| Action（行动） | 选择并调用工具 | 结构化工具调用（JSON） |
| Observation（观察） | 获取工具返回结果 | 工具返回的数据 |

#### ReAct 循环结构

```text
用户问题
   │
   ▼
Thought 1：分析问题，决定先调用什么工具
   │
   ▼
Action 1：调用工具 A
   │
   ▼
Observation 1：工具 A 返回结果
   │
   ▼
Thought 2：基于 Observation 1，决定下一步
   │
   ▼
Action 2：调用工具 B
   │
   ▼
Observation 2：工具 B 返回结果
   │
   ▼
Thought N：信息充足，可以回答
   │
   ▼
Final Answer：给用户的最终回复
```

#### ReAct Prompt 结构设计

一个完整的 ReAct Prompt 应包含五部分：

1. **角色设定**：明确 Agent 身份与能力边界
2. **工具列表**：清晰描述每个工具的名称、参数、返回值
3. **循环规则**：明确 Thought-Action-Observation 的输出格式
4. **终止条件**：何时输出 Final Answer，何时停止
5. **安全约束**：工具调用前的 Thought 解释、错误处理

> **与 Day04 ReAct 模板的关系**：Day04 的 `03-react-pattern.md` 是 ReAct 概念入门；本章 `01-react-agent.md` 是完整 Agent 模板，含系统设定、循环控制、异常处理等工程化要素。

### 3. 工具描述格式（Function Calling Schema）

工具描述是 Agent 的"接口契约"——LLM 完全依赖工具描述来决定调用哪个工具、传什么参数。描述不清是 Agent 失败的首要原因。

#### 工具描述四要素

| 要素 | 说明 | 示例 |
|------|------|------|
| 工具名称 | 动词 + 名词，语义清晰 | `query_order` / `create_ticket` |
| 工具描述 | 一句话说明用途、适用场景 | "根据订单号查询订单状态、商品、金额等信息" |
| 参数 Schema | 参数名、类型、是否必填、约束 | `order_id: string, required` |
| 返回值 Schema | 返回字段、类型、含义 | `{order_id, status, amount, ...}` |

#### OpenAI Function Calling 格式（JSON Schema）

```json
{
  "name": "query_order",
  "description": "根据订单号查询订单状态、商品、金额等信息。当用户提供订单号或咨询订单进度时调用。",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "订单编号，格式如 20251031-001"
      }
    },
    "required": ["order_id"]
  }
}
```

#### Claude Tool Use 格式（XML 风格）

```xml
<tool_description>
  <tool_name>query_order</tool_name>
  <description>根据订单号查询订单状态、商品、金额等信息。当用户提供订单号或咨询订单进度时调用。</description>
  <parameters>
    <parameter name="order_id" type="string" required="true">
      订单编号，格式如 20251031-001
    </parameter>
  </parameters>
</tool_description>
```

两种格式的核心差异：OpenAI 用 JSON Schema（机器可校验），Claude 用 XML（更易读、更利于 LLM 理解）。两者本质等价，选型取决于目标模型。

### 4. 工具选择 Prompt 设计

#### 工具描述的措辞技巧

工具描述写得好，Agent 选对工具的概率大幅提升。三大技巧：

| 技巧 | 说明 | 反例 → 正例 |
|------|------|-----------|
| 触发条件前置 | 第一句说明"何时调用" | "查询订单" → "当用户提供订单号或咨询订单进度时调用" |
| 参数语义化 | 说明参数含义与格式 | "order_id: string" → "order_id: 订单编号，格式如 20251031-001" |
| 边界明确 | 说明不适用场景 | "查物流" → "查询物流轨迹。注意：仅查询已发货订单，未发货订单请用 query_order" |

#### 多工具场景的优先级控制

当多个工具都"看起来相关"时，通过 Prompt 显式声明优先级：

```text
工具选择优先级：
1. 用户提供了订单号 → 优先调用 query_order
2. 用户询问物流进度 → 调用 query_logistics（需先从 query_order 获取 tracking_no）
3. 用户询问商品是否有货 → 调用 query_inventory
4. 需要跟进处理 → 调用 create_ticket
```

#### "无匹配工具"的处理

Agent 必须知道何时**不调用工具**，否则会强行误用。处理策略：

```text
无匹配工具时的处理：
- 若用户问题超出工具能力范围，直接基于知识库回答，不得强行调用不相关工具
- 若信息不足以调用任何工具（如缺少订单号），向用户追问必要信息
- 不得编造工具或编造工具返回结果
```

### 5. 多步规划与任务分解

复杂任务单轮 ReAct 往往效率低下——反复试错、上下文膨胀。Plan-and-Execute 模式先规划全局，再分步执行，更适合多依赖任务。

#### Plan-and-Execute 模式 vs ReAct 模式

| 维度 | ReAct 模式 | Plan-and-Execute 模式 |
|------|-----------|---------------------|
| 流程 | 边推理边行动 | 先规划全局，再分步执行 |
| 上下文 | 持续累积，易超长 | 规划与执行分离，可控 |
| 适用任务 | 信息收集、单线调查 | 多依赖、多分支复杂任务 |
| 错误恢复 | 每轮可调整 | 需重新规划 |
| 实现复杂度 | 低 | 中 |
| 典型场景 | 查订单 → 查物流 → 回复 | 处理客诉（退款 + 换货 + 赔偿 + 工单） |

#### Plan-and-Execute 四步骤

```text
步骤1：任务分析
   ↓  拆解用户诉求，识别子任务与依赖关系
步骤2：制定执行计划
   ↓  生成有序步骤列表，标注每步所需工具
步骤3：逐步执行
   ↓  按计划依次调用工具，收集结果
步骤4：结果汇总
   ↓  综合所有步骤结果，生成最终回复
```

#### 子任务依赖管理

```text
任务：处理"商品破损要求换货 + 退款运费"客诉

依赖关系图：
┌─────────────┐
│ 查询订单     │ ← 所有后续步骤依赖
└──────┬──────┘
       │
       ├─→ ┌─────────────┐
       │   │ 查询退换货政策│ ← 决定赔偿方案
       │   └──────┬──────┘
       │          │
       ├─→ ┌─────────────┐
       │   │ 创建换货工单 │ ← 依赖订单 ID + 政策
       │   └──────┬──────┘
       │          │
       └─→ ┌─────────────┐
           │ 创建退款工单 │ ← 依赖订单 ID + 政策
           └─────────────┘
```

#### 动态调整计划

执行过程中若发现计划与实际不符（如订单已退款无法再退），需触发重新规划：

```text
若执行中发现以下情况，需重新规划：
- 关键信息缺失（如订单号不存在）
- 前置步骤结果改变后续路径（如订单已取消，无需再换货）
- 工具调用失败连续 2 次
重新规划时应保留已完成步骤的结果，仅调整未执行部分。
```

### 6. Agent 记忆管理

Agent 的"记忆"决定了它能处理多复杂的任务、能维持多长的对话。三类记忆机制：

| 记忆类型 | 存储 | 生命周期 | 用途 | 实现方式 |
|---------|------|---------|------|---------|
| 短期记忆 | 上下文窗口 | 单次会话 | 当前对话历史、工具调用结果 | messages 列表 |
| 长期记忆 | 向量数据库 / KV 存储 | 跨会话 | 用户画像、历史工单、偏好 | RAG 检索注入 |
| 记忆压缩 | 摘要存储 | 上下文超长时触发 | 防止上下文膨胀 | 滚动摘要 + 关键信息保留 |

#### 记忆压缩策略

当上下文接近窗口上限时，触发压缩：

```text
记忆压缩规则：
1. 保留：最近 3 轮对话原文、所有工具调用的关键结果、用户身份信息
2. 压缩：4 轮以前的对话 → 摘要（≤100 字）
3. 丢弃：寒暄、重复信息、已过期的临时数据
4. 压缩后注入：【历史摘要】字段，置于系统提示之后
```

### 7. 多 Agent 协作 Prompt

复杂任务单 Agent 难以胜任——上下文过长、角色混乱、工具过多。多 Agent 协作将任务拆分给专职 Agent，各司其职。

#### 角色分工原则

| 分工维度 | 说明 | 示例 |
|---------|------|------|
| 按职能 | 不同 Agent 负责不同环节 | 意图识别 / 信息查询 / 回复生成 |
| 按领域 | 不同 Agent 掌握不同知识 | 售前咨询 / 售后处理 / 物流查询 |
| 按权限 | 不同 Agent 拥有不同工具 | 只读 Agent / 可写 Agent / 审批 Agent |

#### 三种协作模式

| 模式 | 流程 | 适用场景 | 优势 | 劣势 |
|------|------|---------|------|------|
| 串行 | A → B → C 依次传递 | 流程固定、有明确顺序 | 简单可控、易调试 | 延迟高、无并行 |
| 并行 | A、B 同时执行 → 汇总 | 子任务独立、无依赖 | 速度快 | 结果合并复杂 |
| 层级 | 主 Agent 调度子 Agent | 复杂任务、需动态分配 | 灵活、可扩展 | 实现复杂、成本高 |

#### Agent 间通信协议

多 Agent 协作必须约定通信格式，避免"鸡同鸭讲"：

```text
Agent 间消息格式：
{
  "from": "intent_agent",
  "to": "query_agent",
  "task": "查询订单",
  "params": {"order_id": "20251031-001"},
  "context": "用户咨询物流延迟，已识别意图为 order_query",
  "required_output": "订单状态 + 物流轨迹"
}
```

### 8. 自我反思与修正（Reflection）

Reflection 让 Agent "审视自己的输出"——生成 → 评估 → 修正 → 再生成。这是提升 Agent 输出质量的低成本高收益手段。

#### Reflection 工作流

```text
步骤1：生成初始回复
   ↓  基于用户问题与工具结果生成初版回复
步骤2：评估回复质量
   ↓  按维度评估：准确性 / 完整性 / 安全性 / 语气
步骤3：修正（若有问题）
   ↓  针对评估发现的问题逐条修正
步骤4：输出最终版本
   ↓  输出修正后的版本作为最终回复
```

#### Reflection Prompt 结构

```text
你是一个客服回复质量审核员。请评估以下客服回复，按维度打分并指出问题。

【用户问题】{{user_message}}
【客服回复】{{draft_reply}}
【工具结果】{{tool_results}}

评估维度（每项 1-5 分）：
1. 准确性：是否与工具结果一致，有无编造
2. 完整性：是否回答了用户所有问题
3. 安全性：是否泄露系统信息、是否违反安全规则
4. 语气：是否符合客服规范、是否专业友善

输出 JSON：
{
  "scores": {"accuracy": 5, "completeness": 4, "safety": 5, "tone": 5},
  "issues": ["问题1", "问题2"],
  "revised_reply": "修正后的回复（无问题则与原文相同）"
}
```

### 9. Agent 循环控制

Agent 失败的常见原因之一是"无限循环"——反复调用同一工具、或始终无法给出 Final Answer。循环控制是工程化的必备环节。

| 控制点 | 规则 | 示例 |
|-------|------|------|
| 最大循环次数 | 超出后强制终止 | "最多循环 5 次，超出后基于已有信息给 Final Answer" |
| 重复检测 | 同一工具 + 同一参数不重复调用 | "不得重复调用相同工具与参数" |
| 错误重试 | 连续失败 N 次转人工 | "工具调用失败连续 2 次，转人工处理" |
| 超时控制 | 单轮响应超时 | 工程层面实现，Prompt 中说明"若无法解决请转人工" |
| 终止信号 | 明确 Final Answer 格式 | "信息充足时必须输出 Final Answer: ..." |

### 10. Agent 应用场景

| 场景 | 核心工具 | 典型流程 | 价值 |
|------|---------|---------|------|
| 自动编程 | 文件读写、终端、搜索 | 需求分析 → 编码 → 测试 → 调试 | 释放重复编码工作 |
| 数据分析 | SQL、Python、可视化 | 提需求 → 查数据 → 分析 → 出图 | 降低分析门槛 |
| 智能客服 | 订单查询、工单、知识库 | 意图识别 → 查询 → 回复 → 跟进 | 7×24 自动响应 |
| 自动搜索 | 搜索引擎、网页抓取 | 提问 → 搜索 → 阅读 → 综合 | 实时信息整合 |
| 流程自动化 | 邮件、日历、审批 | 接收指令 → 执行 → 反馈 | 跨系统打通 |

## 关键知识点总结

### ReAct 循环流程图

```text
┌─────────────────────────────────────────────────────────┐
│                    ReAct Agent 循环                      │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
                 ┌────────────────┐
                 │   接收用户问题  │
                 └────────┬───────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  Thought：分析现状     │ ← 第 N 轮
              │  决定下一步行动        │
              └───────────┬───────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  Action：调用工具      │
              │  输出 JSON 工具调用    │
              └───────────┬───────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  Observation：工具返回 │
              │  环境反馈结果          │
              └───────────┬───────────┘
                          │
                   ┌──────┴──────┐
                   │ 信息充足？  │
                   └──────┬──────┘
                  否 │         │ 是
                     ▼         ▼
              (回到 Thought)  ┌──────────────────┐
                              │ Final Answer     │
                              │ 输出最终回复      │
                              └──────────────────┘

循环控制：
- 最多 5 轮，超出强制终止
- 同一工具+参数不重复调用
- 连续 2 次失败转人工
```

### 工具描述 Schema 模板

```text
工具名：{verb}_{noun}（动词_名词）
描述：[触发条件] + [功能说明] + [边界/不适用场景]
参数：
  - {param_name}（{type}, {required/optional}）：[含义 + 格式 + 示例]
返回：
  - {field_name}（{type}）：[含义]

示例：
工具名：query_order
描述：当用户提供订单号或咨询订单进度时调用。返回订单状态、商品、金额等信息。
      不适用于物流轨迹查询（请用 query_logistics）。
参数：
  - order_id（string, required）：订单编号，格式如 20251031-001
返回：
  - order_id（string）：订单编号
  - status（string）：订单状态
  - amount（number）：订单金额
  - product（string）：商品名称
```

### Agent 记忆管理速查

| 场景 | 策略 | 实现要点 |
|------|------|---------|
| 单轮简单任务 | 仅短期记忆 | 保留当前对话 + 工具结果 |
| 多轮复杂任务 | 短期 + 压缩 | 超过 N 轮触发摘要压缩 |
| 跨会话个性化 | 短期 + 长期 | 向量库存用户画像，RAG 注入 |
| 长期任务跟踪 | 三者结合 | 工单状态持久化 + 会话摘要 + 当前上下文 |

压缩原则：**保留关键事实、压缩冗余对话、丢弃过期信息**。

### 多 Agent 协作模式对比表

| 模式 | 流程图 | 延迟 | 实现难度 | 适用场景 |
|------|--------|------|---------|---------|
| 串行 | A → B → C | 高（累加） | 低 | 流程固定、顺序明确 |
| 并行 | A ┐<br>B ┘→ 汇总 | 低（取最大） | 中 | 子任务独立、无依赖 |
| 层级 | 主 Agent → 子 Agent | 中 | 高 | 复杂任务、动态分配 |

选型建议：**默认串行，独立子任务用并行，复杂动态用层级**。

## 实战练习

### 练习 1：扩展 ReAct Agent 工具集

**任务**：
1. 基于 `Code/01-react-agent.md` 的 ReAct 模板，新增 2 个工具：`query_user_profile(user_id)`（查询用户等级与历史订单）和 `apply_compensation(order_id, type, amount)`（申请补偿）
2. 编写完整的工具描述（OpenAI Function Calling 格式）
3. 设计一个新场景：VIP 用户投诉物流破损，Agent 需查询订单 → 查询用户等级 → 查询退换货政策 → 申请补偿 → 生成回复
4. 写出完整的 4 轮 Thought-Action-Observation 循环

**验收标准**：
- 工具描述含触发条件、参数格式、返回字段
- ReAct 循环不少于 4 轮
- VIP 用户与普通用户的处理策略有差异（如补偿额度不同）

### 练习 2：多 Agent 协作处理退款客诉

**任务**：
1. 基于 `Code/04-multi-agent-collaboration.md`，设计一个 4 Agent 协作系统：意图识别 Agent → 订单查询 Agent → 政策匹配 Agent → 回复生成 Agent
2. 编写每个 Agent 的 System Prompt（角色 + 工具 + 输出格式）
3. 定义 Agent 间通信协议（JSON 格式）
4. 模拟一个用户案例："我买的耳机 3 天就坏了，要退款"，跑通 4 个 Agent 的串行流程

**验收标准**：
- 每个 Agent 有明确的输入输出 Schema
- 通信协议 JSON 格式规范、字段完整
- 4 个 Agent 协作完成完整退款流程

### 练习 3：客服 Agent 完整系统设计

**任务**：
1. 基于 `Code/06-customer-service-agent.md`，设计你所在行业（或熟悉的领域）的客服 Agent 系统
2. 包含：系统角色 + 至少 5 个工具 + 安全护栏 + 对话历史管理 + 异常处理 + 2 个多轮对话示例
3. 设计 Reflection 自检环节：在生成回复后自动评估质量并修正
4. 编写测试用例：正常咨询 / 工具失败 / 越界请求（要求泄露系统信息）各 1 个

**验收标准**：
- 工具描述完整、可被 LLM 正确选择
- 安全护栏能拦截越界请求
- Reflection 环节能识别并修正至少 1 类问题
- 测试用例覆盖正常 / 异常 / 越界三种场景
