# Token 与上下文窗口演示

> 本文件用具体文本演示 Token 计数、不同语言 Token 消耗对比、以及上下文窗口的管理策略（长文本截断 / 分块 / 摘要压缩）。所有 Prompt 模板可直接用于主流 LLM。

---

## 一、Token 计数演示

### 模板说明
- 用途：演示同一段文本在不同模型下的 Token 计数差异
- 适用模型：GPT-4 / Claude / 通用
- 变量：`{{text}}`

### 完整模板（Token 计数说明 Prompt）
```
请对以下文本进行 Token 分析：

文本：
"""
{{text}}
"""

请输出：
1. 该文本的字符数（中文字符 + 英文字符 + 数字 + 标点）
2. 估算在 GPT-4 (cl100k_base) 下的 token 数
3. 估算在 GPT-4o (o200k_base) 下的 token 数
4. 估算在国内中文优化模型下的 token 数

以表格输出结果。
```

### 使用示例
#### 输入
```
请对以下文本进行 Token 分析：

文本：
"""
尊敬的客户您好，您于 2024 年 5 月 1 日下单的"无线蓝牙耳机"已发货，
物流单号 SF1234567890，预计 5 月 3 日送达。如有疑问请联系客服。
"""

请输出：
1. 该文本的字符数（中文字符 + 英文字符 + 数字 + 标点）
2. 估算在 GPT-4 (cl100k_base) 下的 token 数
3. 估算在 GPT-4o (o200k_base) 下的 token 数
4. 估算在国内中文优化模型下的 token 数

以表格输出结果。
```

#### 预期输出
| 维度 | 数值 |
|------|------|
| 字符数 | 约 78 |
| GPT-4 (cl100k_base) | 约 110-120 token |
| GPT-4o (o200k_base) | 约 80-90 token |
| 国内中文模型 | 约 78-85 token |

> 说明：GPT-4 的 cl100k_base 对中文切分较碎，1 个汉字常占 1-2 token；GPT-4o 的 o200k_base 优化了多语言，中文 token 消耗下降约 30%；国内模型对中文优化最好，1 汉字≈1 token。

### 调优建议
- 准确计数请用 `tiktoken`（见 `Code/README.md`），人工估算仅供参考
- 中文场景优先选 GPT-4o 或国内模型，可显著降低 token 成本

## 二、不同语言 Token 消耗对比

### 模板说明
- 用途：对比中英文、混合文本的 Token 消耗
- 适用模型：通用
- 变量：无（演示用）

### 对比数据

| 文本 | 字符数 | GPT-4 token | GPT-4o token | 国内模型 token |
|------|--------|-------------|--------------|---------------|
| `I want a refund` | 15 | 5 | 5 | 5 |
| `我想退货` | 4 | 4-6 | 4 | 4 |
| `订单号 SO20240501 已发货，预计 5 月 3 日送达` | 25 | 35-45 | 25-30 | 25 |
| `The order SO20240501 has been shipped and will arrive on May 3.` | 64 | 17 | 17 | 17 |

**关键结论**：
- 纯英文：所有模型 token 接近，约 1 token ≈ 4 字符
- 纯中文：GPT-4 消耗最高（1 汉字 ≈ 1.5 token），国内模型最低（1 汉字 ≈ 1 token）
- 中英混合（含数字/编号）：GPT-4 对中文部分切分碎，整体 token 偏高
- **成本估算公式**（GPT-4 中文场景）：`token ≈ 字数 × 1.5`

### 演示 Prompt（让 LLM 自行对比）
```
请对比以下三段文本的 token 消耗（基于 GPT-4 的 cl100k_base 分词器估算）：

文本 A（英文）：I want to return the order SO20240501.
文本 B（中文）：我想退掉订单 SO20240501。
文本 C（中英混合）：Order SO20240501 的退款申请已提交，please wait for review.

请输出每段文本的：字符数、估算 token 数、token/字符比，并说明哪种文本 token 消耗最高。
```

#### 预期输出
```
文本 A：字符 38，token 约 12，比 0.32
文本 B：字符 19，token 约 18，比 0.95
文本 C：字符 50，token 约 35，比 0.70

结论：纯中文（文本 B）token/字符比最高，因为 GPT-4 对中文切分较碎；
纯英文（文本 A）比最低，英文 token 利用率最高。
```

### 调优建议
- 大量中文文本场景，优先选 GPT-4o / 国内模型以降低成本
- 若必须用 GPT-4，可考虑将高频中文 prompt 模板做精简，去除冗余修饰

## 三、上下文窗口管理策略

当文本超过模型上下文窗口，或为控制成本时，需采用管理策略。下面演示三种主流方式。

### 策略 1：长文本截断（Truncation）

#### 模板说明
- 用途：当输入超过窗口时，保留最相关的部分
- 适用模型：通用
- 变量：`{{long_text}}`、`{{max_tokens}}`

#### 完整模板
```
你是 SmartCS 客服摘要助手。下方是一段过长的用户投诉记录，请截取其中与"退款"直接相关的关键段落，
总长度不超过 {{max_tokens}} 字，保留时间、订单号、问题描述等关键信息。

用户投诉记录：
"""
{{long_text}}
"""

输出：仅输出截取后的关键段落，不要添加解释。
```

#### 使用示例
##### 输入
```
你是 SmartCS 客服摘要助手。下方是一段过长的用户投诉记录，请截取其中与"退款"直接相关的关键段落，
总长度不超过 100 字，保留时间、订单号、问题描述等关键信息。

用户投诉记录：
"""
2024 年 5 月 1 日 10:00，用户小李进入直播间观看带货。10:30 下单购买无线蓝牙耳机一台，订单号 SO20240501-001。
5 月 3 日收到商品。5 月 4 日使用时发现左耳有杂音。5 月 5 日联系客服要求退款，客服 A 表示需检测。
5 月 6 日用户再次催促，表示如果两天内不退款将投诉到 12315。用户情绪激动，多次强调"必须退款"。
"""

输出：仅输出截取后的关键段落，不要添加解释。
```

##### 预期输出
```
5 月 1 日下单蓝牙耳机，订单号 SO20240501-001。5 月 4 日发现左耳有杂音，5 月 5 日申请退款未果，5 月 6 日催促要求两天内退款，否则投诉 12315。
```

#### 调优建议
- 截断会丢失信息，仅适合对完整性要求不高的场景
- 截断时优先保留首尾（时间、订单号、结论），舍弃中段铺垫

---

### 策略 2：分块处理（Chunking）

#### 模板说明
- 用途：将长文本切成多块，逐块处理后再合并
- 适用模型：通用
- 变量：`{{chunk}}`、`{{chunk_index}}`、`{{total_chunks}}`

#### 完整模板
```
你是 SmartCS 客服文本分析助手。下方是长文本的第 {{chunk_index}} / {{total_chunks}} 块。
请提取该块中的"用户诉求"与"情绪强度（1-5）"。

文本块：
"""
{{chunk}}
"""

输出 JSON：{"claims": ["诉求1", ...], "emotion_score": 1-5}
```

#### 使用示例
##### 输入
```
你是 SmartCS 客服文本分析助手。下方是长文本的第 2 / 3 块。
请提取该块中的"用户诉求"与"情绪强度（1-5）"。

文本块：
"""
5 月 4 日使用时发现左耳有杂音，严重影响使用。我要求立即退款，不要再让我等检测了！
"""

输出 JSON：{"claims": ["诉求1", ...], "emotion_score": 1-5}
```

##### 预期输出
```json
{"claims": ["立即退款", "不再等待检测"], "emotion_score": 4}
```

#### 合并策略
对 3 个分块分别得到结果后，再用一个合并 Prompt：
```
以下是 3 段文本块的分析结果，请合并为最终结论：
块1：{"claims": [...], "emotion_score": 3}
块2：{"claims": [...], "emotion_score": 4}
块3：{"claims": [...], "emotion_score": 5}

输出：{"main_claim": "...", "avg_emotion": ..., "trend": "..."}
```

#### 调优建议
- 分块大小建议 500-1000 token，过小则上下文不足，过大则失去分块意义
- 分块时尽量在自然段落/句子边界切分，避免截断语义

### 策略 3：摘要压缩（Summarization）

#### 模板说明
- 用途：将长对话/长文档压缩为摘要，腾出上下文空间
- 适用模型：GPT-4 / Claude / 通用
- 变量：`{{conversation}}`

#### 完整模板
```
你是 SmartCS 客服对话摘要助手。请将以下客服对话压缩为一段不超过 150 字的摘要，
保留：用户身份、订单号、核心诉求、当前处理进度、待办事项。

对话记录：
"""
{{conversation}}
"""

输出格式：
- 用户：...
- 订单：...
- 诉求：...
- 进度：...
- 待办：...
```

#### 使用示例
##### 输入
```
你是 SmartCS 客服对话摘要助手。请将以下客服对话压缩为一段不超过 150 字的摘要，
保留：用户身份、订单号、核心诉求、当前处理进度、待办事项。

对话记录：
"""
用户：我买的耳机有杂音，订单 SO20240501-001，要退款。
客服：您好，已收到您的退款申请，请提供商品照片。
用户：[发送照片] 左耳有明显杂音。
客服：照片已收到，我将为您提交退款工单，预计 1-3 个工作日到账。
用户：好的，请尽快。
"""

输出格式：
- 用户：...
- 订单：...
- 诉求：...
- 进度：...
- 待办：...
```

##### 预期输出
```
- 用户：小李
- 订单：SO20240501-001（无线蓝牙耳机）
- 诉求：因商品杂音申请退款
- 进度：已提交退款工单，照片已上传
- 待办：跟进 1-3 工作日退款到账情况
```

#### 调优建议
- 摘要压缩是多轮对话管理的关键技术：早期对话压缩成摘要，新对话基于摘要继续
- 温度建议：0.2（摘要需准确，不要发挥）
- 摘要后可让模型自检："摘要是否遗漏关键信息？"

## 四、上下文窗口占用估算表

| 场景 | 输入 token | 输出 token | 单次总 token | 128K 窗口可承载轮数（粗估） |
|------|-----------|-----------|-------------|---------------------------|
| 单轮 FAQ 问答 | 500 | 200 | 700 | 约 180 轮 |
| 带长 FAQ 知识库 | 8000 | 300 | 8300 | 约 15 轮 |
| 多轮对话（累积 10 轮） | 5000 | 1000 | 6000 | — |
| 整篇商品说明书 | 30000 | 500 | 30500 | 约 4 轮 |

> 实际开发中应监控每次请求的 token 消耗，超过窗口 80% 时触发摘要压缩或截断。

---

## 总结

| 策略 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| 截断 | 信息完整性要求低 | 简单、快 | 丢信息 |
| 分块 | 需完整处理长文本 | 保完整 | 多次调用、成本高 |
| 摘要压缩 | 多轮对话管理 | 节省 token | 可能丢细节 |

> 实战中常组合使用：近期对话保留原文 + 早期对话压缩为摘要 + 超长文档用 RAG 按需检索。
