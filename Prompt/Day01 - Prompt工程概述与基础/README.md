# Day01 - Prompt 工程概述与基础

Prompt Engineering 是与大语言模型（LLM）高效沟通的核心技能——它决定了 LLM 输出质量的上限。同样一个 GPT-4 或 Claude，用"帮我看看这个"得到的是泛泛而谈，而用"以电商客服身份，将以下用户投诉归类为退款/换货/维修三类并输出 JSON"得到的则是可直接用于业务的精准结果。本章将从 LLM 的工作原理讲起，厘清 Token、上下文窗口、温度等基础概念，揭示 Prompt 的本质是"指令"而非"搜索查询"，并围绕智能客服助手 SmartCS 场景演示 Prompt 四要素、对话角色体系与多轮对话机制，为后续设计原则与高级技巧打下地基。

## 学习目标

- 理解 LLM 的工作原理：Token 化、上下文窗口、温度、概率模型本质
- 掌握 Prompt 的本质：指令而非搜索查询，引导 LLM 在概率空间中找到正确方向
- 能准确表述 Prompt Engineering 的定义与发展历程
- 理解为什么需要 Prompt Engineering，能给出好 Prompt 与差 Prompt 的对比
- 掌握 Prompt 基本结构四要素：指令、上下文、输入、输出格式
- 理解对话角色体系（System / User / Assistant）及协作关系
- 掌握多轮对话机制：上下文累积与遗忘
- 能对比主流 LLM（GPT-4 / Claude 3.5 / Gemini / 文心一言 / 通义千问 / 智谱清言）的特点与适用场景

## 理论知识讲解

### 1. LLM 工作原理

要写好 Prompt，必须先理解 LLM 在底层到底做了什么。LLM 不是知识库，不是搜索引擎，而是一个**基于概率预测下一个 Token** 的语言模型。

#### 1.1 Token 化（Tokenization）

LLM 不直接理解"字符"或"单词"，它处理的最小单位是 **Token**。一段文本送入模型前，会先被切分成 Token 序列，再映射为高维向量，最后基于这些向量预测下一个 Token。

```
文本 → Token 切分 → Token ID → 向量（Embedding） → 预测下一个 Token
```

不同模型的 Token 切分方式不同：

| 模型 | 分词器 | 特点 |
|------|--------|------|
| GPT-3.5 / GPT-4 | tiktoken (BPE) | 英文约 1 token ≈ 4 字符；中文 1 个汉字常占 1-2 token |
| GPT-4o | tiktoken `o200k_base` | 对中文更友好，汉字 token 消耗下降 |
| Claude | Anthropic 内置分词器 | 与 GPT 不同，长文本下 token 计数有差异 |
| 国内模型 | 各自分词器 | 通常对中文优化，1 个汉字常≈1 token |

**关键结论**：中文 token 消耗普遍大于英文。同样一句"我想退货"，英文 "I want a refund" 用 tiktoken 约 5 token，中文"我想退货"可能需要 4-6 token。这直接影响成本估算与上下文窗口占用。

#### 1.2 上下文窗口（Context Window）

上下文窗口是模型一次推理能处理的最大 Token 数（输入 + 输出）。超过窗口的内容会被截断或遗忘。

| 模型 | 上下文窗口 | 说明 |
|------|-----------|------|
| GPT-4 Turbo | 128K | 约 9.6 万英文单词 |
| GPT-4o | 128K | 速度更快、价格更低 |
| Claude 3.5 Sonnet | 200K | 长文档处理优势明显 |
| Gemini 1.5 Pro | 1M / 2M | 超长上下文，可处理整本书 |
| 文心一言 4.0 | 8K-128K | 中文场景友好 |
| 通义千问 Max | 32K-128K | 阿里云生态集成 |
| 智谱清言 GLM-4 | 128K | 国产长上下文模型 |

上下文长度对成本和效果的影响：

- **成本**：API 按 token 计费，输入越长费用越高，且长上下文推理更慢
- **效果**：并非越长越好——上下文过长时存在"中间遗忘"现象（Lost in the Middle），模型对开头和结尾的信息记忆更牢
- **策略**：长文本需分块（chunking）、摘要压缩、检索增强（RAG）只送入相关片段

#### 1.3 温度（Temperature）

温度控制模型采样的随机性，取值通常为 0-2。

- **Temperature = 0**：几乎确定性输出（贪婪解码），每次得到相同结果，适合分类、抽取、代码生成
- **Temperature = 1**：高随机性，输出更多样、更有创意，适合头脑风暴、创意写作
- **Temperature = 0.7**：平衡准确与创意，适合对话、客服回复

**Top-p（核采样）** 是另一种采样控制：只从累积概率达到 p 的候选 token 中采样。`top_p=0.9` 表示忽略概率极低的长尾 token。通常 Temperature 与 Top-p 二选一调整，不要同时大幅改动。

#### 1.4 概率模型本质

> **LLM 是概率预测器，不是知识库。**

LLM 在生成每个 Token 时，是在所有候选词上输出一个概率分布，然后按分布采样。这意味着：

- LLM 可能"一本正经地胡说八道"（幻觉，Hallucination）
- LLM 的回答是概率最高的续写，不一定是事实正确的
- 同一个问题不同次提问可能得到不同答案（Temperature > 0 时）
- Prompt 的作用是**引导模型从概率空间中找到正确方向**——给的条件越精确，正确答案所在的概率区间越被强化

### 2. Prompt 的本质

很多人把 Prompt 当成"搜索查询"，认为输入"退货流程"模型就会返回退货流程文档。这是误解。

> **Prompt 是"指令"（Instruction），不是"搜索查询"（Search Query）。**

- 搜索查询：告诉搜索引擎"我要找什么"，它返回最匹配的已有网页
- Prompt：告诉 LLM "你要做什么、怎么做、按什么格式输出"，它**生成**一个回答

Prompt 的本质是用自然语言编写的一段"程序"，它引导 LLM 从巨大的概率空间中收敛到我们想要的输出区域。好的 Prompt 像一份精确的任务说明书，差的 Prompt 像一句模糊的自言自语。

### 3. Prompt Engineering 定义

> **Prompt Engineering（提示词工程）**：设计和优化 LLM 输入指令，以稳定、可控地获得期望输出的系统工程方法。

它不是"写一句话让 AI 回答"，而是一个包含设计、测试、评估、迭代的工程过程，关注：输出准确性、格式可控性、稳定性（多次运行一致）、成本效率、安全性。

### 4. 为什么需要 Prompt Engineering

同一 LLM，不同 Prompt 产出差距巨大。下面是 SmartCS 客服场景的对比：

**差 Prompt（客服问候）**：
```
你好
```
预期输出：`你好！有什么可以帮您的吗？`（泛泛、无业务感）

**好 Prompt（客服问候）**：
```
你是电商平台 SmartCS 的客服助手。请用专业、热情、简洁的语气，
向刚进店的用户发送一段不超过 30 字的欢迎语，包含店铺名称与一句引导提问。
```
预期输出：`欢迎来到 SmartCS！选购中遇到任何商品、订单或售后问题，都可以直接问我哦～`

**差 Prompt（商品推荐）**：
```
推荐个手机
```
预期输出：一份通用手机清单，与用户需求无关

**好 Prompt（商品推荐）**：
```
你是 SmartCS 的导购助手。根据用户画像（预算 3000 元、偏好拍照、续航要好），
从以下在售机型中推荐 2 款，输出 JSON 数组，每项含 name、price、reason 三字段。
可选机型：[PhoneA 2999 拍照旗舰 / PhoneB 3199 大电池 / PhoneC 2599 性价比]
```
预期输出：结构化 JSON，直接可被业务系统消费。

### 5. Prompt 的基本结构四要素

一个完整的 Prompt 通常包含四个部分：

| 要素 | 作用 | 示例 |
|------|------|------|
| 指令（Instruction） | 告诉 LLM 做什么 | "对以下用户消息进行意图分类" |
| 上下文（Context） | 提供背景信息 | "你是电商客服系统，意图类别包括：退款、咨询、投诉" |
| 输入（Input） | 待处理的具体内容 | "用户消息：{{user_message}}" |
| 输出格式（Output Format） | 期望的输出形式 | "以 JSON 输出 {intent, confidence}" |

一个结构完整的 SmartCS 意图识别 Prompt：

```
你是 SmartCS 电商客服的意图识别模块。（上下文）
请对用户消息进行意图分类，类别仅限：faq / order_query / refund / complaint / ticket。（指令）

用户消息：{{user_message}}（输入）

以 JSON 输出，格式为 {"intent": "...", "confidence": 0.0-1.0}，不要输出其他内容。（输出格式）
```

四要素并非每次都必须显式写出，但缺失时模型只能靠猜测补全，输出稳定性会下降。

### 6. 对话角色体系

主流 LLM API 采用三角色对话模型：

| 角色 | 作用 | 优先级 |
|------|------|--------|
| System | 设定 LLM 身份、行为规范、护栏 | 最高 |
| User | 用户输入 | 中 |
| Assistant | LLM 的回复，也可作为对话历史回传 | 低（但影响后续） |

- **System Prompt**：定义"你是谁、该做什么、不该做什么"。优先级最高，用于设定客服身份、语气、安全边界。例如：`你是 SmartCS 客服，只回答电商售后问题，拒绝政治、色情等无关话题。`
- **User Prompt**：用户当下的输入，如 `我想退货订单 12345`
- **Assistant**：LLM 上一轮的回复。把历史 Assistant 消息一并传入，模型才能理解上下文（如"它"指代上一轮提到的订单）

三者协作：System 划定边界 → User 提出需求 → Assistant 响应 → 历史 Assistant 提供上下文 → User 追问。

### 7. 多轮对话机制

LLM 本身是无状态的——它不记得任何历史对话。所谓"多轮对话"，是**应用层把历史消息连同新输入一起重新发给模型**。

- **上下文累积**：每轮对话都把之前的 User/Assistant 消息拼接到请求里，模型据此理解上下文
- **上下文遗忘**：当累积超过上下文窗口时，最早的消息会被截断；同时模型对超长上下文存在"中间遗忘"
- **成本累积**：多轮对话越往后，每次请求的输入 token 越多，费用越高

管理策略：限制保留的轮数、对早期对话做摘要压缩、用 RAG 把关键事实存入外部库按需检索。

### 8. 主流 LLM 对比

| 模型 | 上下文窗口 | 特长 | 适用场景 |
|------|-----------|------|---------|
| GPT-4 / GPT-4 Turbo | 128K | 综合能力强、生态成熟、Function Calling 稳定 | 复杂推理、Agent、英文场景 |
| GPT-4o | 128K | 多模态、速度快、价格低 | 实时对话、多模态应用 |
| Claude 3.5 Sonnet | 200K | 长文档、写作、代码、遵循指令好 | 长文本分析、结构化输出 |
| Gemini 1.5 Pro | 1M-2M | 超长上下文、多模态 | 整书处理、视频理解 |
| 文心一言 4.0 | 8K-128K | 中文友好、百度生态 | 中文业务、合规场景 |
| 通义千问 Max | 32K-128K | 阿里云集成、中文强 | 企业应用、阿里云生态 |
| 智谱清言 GLM-4 | 128K | 国产长上下文、Agent 能力 | 国产化部署、Agent |

选型建议：海外项目优先 GPT-4 / Claude；国内合规项目选文心 / 通义 / 智谱；超长文档选 Gemini / Claude；Agent 与工具调用优先 GPT-4 / Claude / GLM-4。

### 9. Prompt Engineering 发展历程

```
简单问答 → Few-Shot（2020 GPT-3）→ CoT 思维链（2022）→ Agent / 工具调用（2023）→ 自动优化（DSPy 等，2024+）
```

- **简单问答**：直接问、直接答，依赖模型预训练知识
- **Few-Shot**：用示例引导模型归纳模式，无需微调
- **CoT**：让模型"逐步思考"，显著提升推理任务表现
- **Agent**：LLM 作为推理引擎，调用外部工具、多步规划
- **自动优化**：用算法自动搜索/优化 Prompt，减少人工试错

## 关键知识点总结

### Prompt 四要素速查

| 要素 | 核心问题 | 缺失后果 |
|------|---------|---------|
| 指令 | 做什么？ | 模型不知道任务目标 |
| 上下文 | 背景？ | 模型靠猜测，输出偏题 |
| 输入 | 处理谁？ | 模型无对象可处理 |
| 输出格式 | 要什么形式？ | 输出不可控、难解析 |

### 主流 LLM 对比速查

| 模型 | 窗口 | 强项 |
|------|------|------|
| GPT-4o | 128K | 多模态、Agent |
| Claude 3.5 | 200K | 长文档、结构化 |
| Gemini 1.5 | 1M+ | 超长上下文 |
| 文心 4.0 | 128K | 中文合规 |
| 通义 Max | 128K | 阿里云生态 |
| GLM-4 | 128K | 国产 Agent |

### Token 消耗估算指南

- 英文：约 1 token ≈ 4 字符 ≈ 0.75 单词
- 中文：1 个汉字约 1-2 token（GPT 系）；国内模型常 1 汉字 ≈ 1 token
- 估算公式：中文 token ≈ 字数 × 1.5（GPT）/ 字数 × 1.0（国内模型）
- 1K token 约能容纳：500-700 中文字 或 750 英文单词

### 对话角色速查

| 角色 | 一句话 | 优先级 |
|------|--------|--------|
| System | "你是谁、能做什么" | 最高 |
| User | "用户要什么" | 中 |
| Assistant | "之前的回复" | 历史上下文 |
