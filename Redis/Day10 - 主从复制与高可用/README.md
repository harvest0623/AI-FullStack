# Day10 - 主从复制与高可用

单机 Redis 即使有持久化，也无法解决两个问题：**单点故障**（进程挂了服务不可用）和**单机容量瓶颈**（单实例内存上限）。生产环境必须引入多实例架构，让 Redis 具备故障自愈与水平扩展能力。Redis 提供三大高可用方案：**主从复制**（数据冗余 + 读写分离）、**Sentinel 哨兵**（自动故障转移）、**Cluster 集群**（分片 + 高可用）。本章将系统讲解三者的原理、部署方式与选型策略。

---

## 学习目标

- 理解主从复制的全量同步与增量同步流程，知道何时触发 PSYNC
- 掌握复制积压缓冲区的作用与配置
- 理解读写分离的收益与主从延迟问题
- 理解 Sentinel 的四大角色：监控、通知、自动故障转移、配置中心
- 区分主观下线（SDOWN）与客观下线（ODOWN）
- 掌握故障转移流程：选 Leader → 选新主 → 通知从节点 → 通知客户端
- 理解 Cluster 的 16384 槽位分片、CRC16 路由、MOVED/ASK 重定向
- 知道集群扩容缩容、hash tag、Gossip 协议
- 能为不同规模业务选择合适的高可用方案

## 理论知识讲解

### 一、主从复制（Replication）

#### 1.1 为什么需要主从

| 痛点 | 单机 | 主从 |
|------|------|------|
| 单点故障 | 实例挂了服务不可用 | 从节点可顶上 |
| 读 QPS 瓶颈 | 单机读上限 ~10 万 | 多从节点分担读 |
| 数据冗余 | 仅依赖持久化 | 实时复制到多节点 |
| 故障恢复基础 | 手动重启 | 为 Sentinel 自动转移铺路 |

#### 1.2 配置方式

**命令行临时配置**（5.0+）：

```
REPLICAOF 127.0.0.1 6379    # 把当前实例设为 127.0.0.1:6379 的从节点
REPLICAOF NO ONE            # 取消从节点身份，变回主节点
```

> 5.0 之前用 `SLAVEOF`，5.0+ 推荐用 `REPLICAOF`（语义更中立），两者等价。

**配置文件持久化**：

```conf
# redis-slave.conf
replicaof 127.0.0.1 6379
replica-read-only yes          # 从节点只读（默认 yes，强烈建议保持）
masterauth yourpassword        # 主节点有密码时从节点需配置
```

#### 1.3 全量同步流程

从节点首次连接主节点或断线后无法增量同步时，触发全量同步：

```
从节点                              主节点
  │                                   │
  │  1. PSYNC ? -1                    │
  ├──────────────────────────────────▶│  （不知道主节点状态，请求全量）
  │                                   │
  │  2. +FULLRESYNC <replid> <offset> │
  │◀──────────────────────────────────┤  （返回主节点复制 ID 与 offset）
  │                                   │
  │                                   │  3. BGSAVE 生成 RDB 快照
  │                                   │     同时把新命令写入复制缓冲区
  │  4. 发送 RDB 文件                  │
  │◀──────────────────────────────────┤
  │                                   │
  │  5. 从节点加载 RDB                 │
  │                                   │
  │  6. 发送缓冲区增量命令              │
  │◀──────────────────────────────────┤
  │                                   │
  │  7. 进入增量同步状态               │
  │◀──────────────────────────────────▶│
```

**触发全量同步的场景**：
- 从节点首次连接主节点
- 从节点断线太久，复制 offset 超出复制积压缓冲区范围
- 主从复制 ID 不匹配（主节点重启后 replid 变化）

#### 1.4 增量同步流程

主从建立连接后，主节点把每条写命令实时同步到从节点。断线重连后若条件满足，可从断点继续同步：

```
从节点                                   主节点
  │                                        │
  │  PSYNC <replid> <offset>               │
  ├───────────────────────────────────────▶│
  │                                        │
  │  +CONTINUE                             │
  │◀───────────────────────────────────────┤
  │                                        │
  │  发送 offset 之后积压的命令              │
  │◀───────────────────────────────────────┤
```

**增量同步条件**：
- 主从复制 ID（replid）一致
- 从节点的 offset 仍在复制积压缓冲区范围内

**复制积压缓冲区**：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `repl-backlog-size` | `1mb` | 缓冲区大小，断线后能增量同步的范围 |
| `repl-backlog-ttl` | `3600` | 所有从节点断开后缓冲区保留秒数 |

> 网络不稳定的环境建议把 `repl-backlog-size` 调大到 32mb 以上，避免频繁全量同步。

#### 1.5 复制 ID 与 offset

- **replid**：主节点的唯一标识，40 字符随机串，重启会变（除非开启 `replid` 持久化）
- **offset**：复制进度，主从各自维护，差值 = 待同步的数据量

查看方式：
```
INFO replication
# 主节点：role:master / connected_slaves:1 / master_replid / master_repl_offset
# 从节点：role:slave / master_host / master_repl_offset / slave_repl_offset
```

#### 1.6 全量 vs 增量同步对比

| 维度 | 全量同步 | 增量同步 |
|------|---------|---------|
| 触发条件 | 首次连接、断线过久、replid 变化 | 断线重连且 offset 在缓冲区内 |
| 数据传输 | 整个 RDB + 缓冲区命令 | 仅 offset 之后的命令 |
| 开销 | 大（fork + RDB 传输 + 加载） | 小 |
| 持续时间 | 长（与数据量正相关） | 短 |

#### 1.7 读写分离

**模式**：主节点负责写，从节点负责读。

```
        ┌────────┐  写   ┌────────┐
客户端 ──▶│ 主节点 │─────▶│ 从节点1 │◀── 读 ── 客户端
        └────────┘      └────────┘
            │           ┌────────┐
            └──────────▶│ 从节点2 │◀── 读 ── 客户端
                        └────────┘
```

**优点**：扩展读 QPS、分担主节点压力
**问题**：
- **主从延迟**：异步复制，从节点数据略滞后（毫秒~秒级），强一致读必须走主
- **读一致性**：写入后立即读，可能从从节点读到旧值
- **连接复杂度**：客户端要区分读写目标

#### 1.8 核心配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `replicaof` | — | 主节点地址 |
| `replica-read-only` | `yes` | 从节点只读 |
| `repl-backlog-size` | `1mb` | 复制积压缓冲区大小 |
| `repl-backlog-ttl` | `3600` | 缓冲区保留时间 |
| `min-replicas-to-write` | `0` | 至少 N 个从节点在线主节点才允许写（防脑裂） |
| `min-replicas-max-lag` | `10` | 上述从节点的最大允许延迟秒数 |
| `masterauth` | — | 主节点密码 |
| `repl-diskless-sync` | `no` | 无盘复制：直接通过 socket 把 RDB 发给从节点 |

### 二、Sentinel 哨兵

#### 2.1 角色与职责

Sentinel 是独立于 Redis 的进程，提供四大能力：

| 角色 | 说明 |
|------|------|
| **监控** | 周期性 PING 主从节点，检测存活状态 |
| **通知** | 把节点状态变化通知运维或客户端 |
| **自动故障转移** | 主节点挂了，自动选一个从升级为新主 |
| **配置中心** | 告诉客户端当前主节点是谁 |

#### 2.2 部署架构

至少部署 **3 个 Sentinel 节点**（奇数个，防止脑裂），与 Redis 节点独立部署：

```
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │Sentinel1 │  │Sentinel2 │  │Sentinel3 │
        └────┬─────┘  └────┬─────┘  └────┬─────┘
             │             │             │
             └─────监控────┼─────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   ┌─────────┐        ┌─────────┐        ┌─────────┐
   │  主节点  │◀──────│ 从节点1  │        │ 从节点2  │
   └─────────┘ 复制   └─────────┘        └─────────┘
```

#### 2.3 主观下线 vs 客观下线

| 概念 | 简称 | 触发条件 |
|------|------|---------|
| **主观下线** | SDOWN | 单个 Sentinel 在 `down-after-milliseconds` 内未收到节点 PING 响应 |
| **客观下线** | ODOWN | `quorum` 个 Sentinel 都判定 SDOWN，则判定 ODOWN |

只有 ODOWN 才会触发故障转移，避免网络抖动误判。

#### 2.4 故障转移流程

```
┌─────────────────────────────────────────────────────┐
│ 步骤 1：达到 ODOWN，触发故障转移                      │
└───────────────────────┬─────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────┐
│ 步骤 2：Sentinel 之间用 Raft 协议选举 Leader         │
│         （负责执行本次故障转移）                       │
└───────────────────────┬─────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────┐
│ 步骤 3：Leader 选新主                                 │
│   优先级：replica-priority 大者胜                    │
│   平级则：复制 offset 大者（数据更新）               │
│   再平级：run_id 字典序小者胜                          │
└───────────────────────┬─────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────┐
│ 步骤 4：Leader 把新主执行 SLAVEOF NO ONE            │
│         通知其他从节点 REPLICAOF 新主                │
└───────────────────────┬─────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────┐
│ 步骤 5：更新配置，通知客户端新主地址                   │
└─────────────────────────────────────────────────────┘
```

#### 2.5 脑裂问题与防护

**脑裂**：原主节点因网络分区暂时"假死"，Sentinel 选了新主；网络恢复后旧主仍以为自己是主，导致双主写入冲突。

**防护**：`min-replicas-to-write` + `min-replicas-max-lag`

```conf
# 主节点必须有至少 1 个从节点延迟 < 10 秒才允许写
min-replicas-to-write 1
min-replicas-max-lag 10
```

网络分区时旧主发现没有从节点在线，会拒绝写入，避免脑裂数据冲突。

#### 2.6 核心配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `sentinel monitor <name> <ip> <port> <quorum>` | — | 监控的主节点名、地址、quorum 数 |
| `sentinel down-after-milliseconds <name> <ms>` | `30000` | SDOWN 判定超时 |
| `sentinel parallel-syncs <name> <n>` | `1` | 故障转移时同时同步新主的从节点数 |
| `sentinel failover-timeout <name> <ms>` | `180000` | 故障转移超时时间 |
| `sentinel auth-pass <name> <pwd>` | — | 主节点密码 |

### 三、Cluster 集群

#### 3.1 为什么需要 Cluster

| 痛点 | 主从/Sentinel | Cluster |
|------|--------------|---------|
| 单机容量 | 数据量受单机内存限制 | 分片，可扩展到 PB |
| 写 QPS | 单主写入上限 | 多主分片，写 QPS 线性扩展 |
| 自动分片 | ❌ | ✅ |
| 故障转移 | Sentinel 集中式 | 节点内置，去中心化 |

#### 3.2 16384 个哈希槽

Cluster 把所有 key 分到 **16384 个槽位（slot）**，每个主节点负责一部分槽位：

```
key → CRC16(key) % 16384 → 槽位号 → 所属节点
```

例如 3 主节点集群的槽位分配：

```
┌──────────────┬──────────────────┐
│   节点       │  槽位范围         │
├──────────────┼──────────────────┤
│  Master A    │  0 - 5460        │
│  Master B    │  5461 - 10922    │
│  Master C    │  10923 - 16383   │
└──────────────┴──────────────────┘
```

#### 3.3 节点通信：Gossip 协议

- 节点间用 **Gossip 协议**交换集群状态信息
- 每个节点除了对外服务端口，还有**集群总线端口 = 客户端端口 + 10000**
- 例如 6379 服务的节点，集群总线端口是 16379

> 部署时务必同时开放两个端口，否则节点间无法通信。

#### 3.4 MOVED 与 ASK 重定向

**MOVED（永久重定向）**：key 不在当前节点，返回正确节点地址，客户端缓存映射后直连：

```
SET stock:product:1001 50
# (error) MOVED 5798 127.0.0.1:6381
# 槽位 5798 归属 127.0.0.1:6381
```

**ASK（临时重定向）**：槽位正在迁移中，临时指向目标节点，客户端不缓存：

```
SET stock:product:1002 30
# (error) ASK 5798 127.0.0.1:6381
```

#### 3.5 集群扩容

新节点加入流程：

```
1. 启动新节点，用 CLUSTER MEET 加入集群
2. redis-cli --cluster reshard 分配槽位
3. 把部分槽位从原节点迁移到新节点
4. （可选）给新主配一个从节点
```

```bash
# 扩容：把 1000 个槽位迁移到新节点 127.0.0.1:7006
redis-cli --cluster reshard 127.0.0.1:7000 \
  --cluster-from <existing_node_id> \
  --cluster-to <new_node_id> \
  --cluster-slots 1000 \
  --cluster-yes
```

#### 3.6 集群缩容

```
1. 把待移除节点的槽位迁移到其他节点
2. 删除节点的从节点（若有）
3. 用 CLUSTER FORGET 移除节点
```

```bash
redis-cli --cluster del-node 127.0.0.1:7000 <node_id>
```

#### 3.7 故障检测与转移

- 节点互相 PING，超时标记 **PFAIL**（Possibly failing）
- 半数以上主节点都标记某节点 PFAIL → 标记 **FAIL**
- 该节点的从节点发起选举，胜者升级为主，接管槽位

选举优先级：`replica-priority` 小者 → `offset` 大者 → `runid` 字典序小者

#### 3.8 Cluster 的限制

| 限制 | 说明 | 解决方案 |
|------|------|---------|
| **只用 DB 0** | 不支持 SELECT 切换库 | 用 key 前缀区分业务 |
| **跨槽位多键操作受限** | MSET / 事务 / Lua 涉及多 key 时所有 key 必须同槽 | hash tag |
| **事务/Lua 限制** | MULTI/EXEC 中所有 key 必须同槽 | 拆分事务 |
| **pub/sub 广播** | PUBLISH 会广播到所有节点 | 用 Stream 替代 |

#### 3.9 Hash Tag（哈希标签）

用 `{}` 包裹 key 的一部分，Cluster 只对 `{}` 内的内容做 CRC16，使相关 key 落在同一槽位：

```
{user:1001}:cart     →  CRC16("user:1001") % 16384
{user:1001}:orders   →  CRC16("user:1001") % 16384
{user:1001}:profile  →  CRC16("user:1001") % 16384

# 三者槽位相同，可在同一事务/Lua 中操作
```

### 四、三种方案对比与选型

| 维度 | 主从复制 | Sentinel | Cluster |
|------|---------|---------|---------|
| **数据冗余** | ✅ | ✅ | ✅ |
| **读写分离** | ✅ | ✅ | ✅ |
| **自动故障转移** | ❌ 手动 | ✅ | ✅ |
| **自动分片** | ❌ | ❌ | ✅ |
| **容量扩展** | 受单机限制 | 受单机限制 | 水平扩展 |
| **客户端复杂度** | 低 | 中（连 Sentinel） | 高（支持 MOVED） |
| **部署复杂度** | 低 | 中 | 高 |
| **适用规模** | 小 | 中 | 大 |

**选型路径**：

```
开发/测试        →  单机
单机够用、要冗余  →  主从（手动运维）
需要自动故障转移  →  Sentinel（1 主 2 从 3 哨兵）
数据量 > 单机内存  →  Cluster（3 主 3 从起）
超高并发写入     →  Cluster（多主分片）
```

## 关键知识点总结

### 三种方案对比表

| 方案 | 故障转移 | 分片 | 最少节点 | 客户端 | 适用 |
|------|---------|------|---------|--------|------|
| 主从 | 手动 | ❌ | 2 | 直连主从 | 小规模冗余 |
| Sentinel | 自动 | ❌ | 3 Redis + 3 Sentinel | 连 Sentinel | 中等规模 |
| Cluster | 自动 | ✅ | 6（3 主 3 从） | 集群客户端 | 大规模 |

### 复制流程图

```
首次连接 / 断线过久：
  从 ──PSYNC ? -1──▶ 主
  主 ──FULLRESYNC replid offset──▶ 从
  主 ──BGSAVE + 发送 RDB──▶ 从
  主 ──发送缓冲区增量──▶ 从

断线重连（offset 在缓冲区内）：
  从 ──PSYNC replid offset──▶ 主
  主 ──+CONTINUE──▶ 从
  主 ──发送 offset 之后命令──▶ 从
```

### 故障转移流程图（Sentinel）

```
SDOWN（单 Sentinel 判定）
   ↓ quorum 个同意
ODOWN（客观下线）
   ↓
Raft 选举 Leader Sentinel
   ↓
Leader 选新主（priority → offset → runid）
   ↓
SLAVEOF NO ONE + 通知从节点复制新主
   ↓
通知客户端新主地址
```

### Cluster 槽位图

```
key = "stock:product:1001"
        │
        ▼
CRC16("stock:product:1001") = 12345
        │
        ▼
12345 % 16384 = 12345
        │
        ▼
槽位 12345 归属 Master C (10923-16383)
        │
        ▼
请求路由到 Master C
```

## 实战练习

### 练习 1：搭建主从并验证复制

需求：参照 `Code/01-replication-setup.md`，用 Docker 启动一主一从：

1. 主节点写入 `SET stock:product:1001 50`
2. 在从节点执行 `GET stock:product:1001`，验证数据已同步
3. 在从节点执行 `SET stock:product:1001 60`，应被拒绝（只读）
4. 主节点 `INCR stock:product:1001`，观察从节点是否能读到新值
5. 思考：异步复制会带来什么一致性问题？

### 练习 2：观察 Sentinel 自动故障转移
