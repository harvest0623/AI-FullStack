# Day11 - 缓存模式与分布式锁

缓存是 Redis 最核心的应用场景，几乎所有高并发系统都会在数据库前面架一层 Redis 缓存来扛住读压力。但"加缓存"远不止 SET/GET 那么简单——选哪种缓存写入策略、如何应对缓存失效带来的三大经典问题、如何在多实例部署下保证同一时刻只有一个进程操作临界资源，这些问题直接决定了系统的稳定性与正确性。分布式锁则是高并发系统的关键组件，从 SETNX 的朴素实现到 SET NX EX 的原子加锁，再到 Lua 脚本安全释放、看门狗续期、Redlock 算法，每一步演进都对应着真实生产事故的教训。本章将系统梳理四种缓存模式的取舍、缓存穿透/击穿/雪崩的成因与对策、缓存一致性方案，以及分布式锁与限流器的完整实现。

- 用 Redis 实现固定窗口、滑动窗口两种限流器

## 一、理论知识：缓存模式

### 1.1 Cache-Aside（旁路缓存）

最常用的缓存模式。应用代码同时操作缓存和数据库，缓存层不主动与数据库交互。

**读流程**：
1. 应用先查缓存
2. 缓存命中 → 直接返回
3. 缓存未命中 → 查数据库 → 写入缓存（带过期时间）→ 返回

**写流程**：
1. 先更新数据库
2. 再删除缓存（注意是删除而非更新，避免并发写导致脏数据）

```
ECHO "=== Cache-Aside 读流程 ==="
GET cache:product:1001                    ; 1. 先查缓存
; 2. 未命中 → 查 DB
SET cache:product:1001 "{...}" EX 3600    ; 3. 回写缓存
```

**优点**：实现简单、职责清晰、缓存失败不影响数据库读写。
**缺点**：首次查询必 miss；缓存与数据库存在短暂不一致窗口。

### 1.2 Read-Through

应用只与缓存层交互，缓存层（通常由客户端库封装）负责自动回源查数据库。

- 应用调用 `cache.get(key)`，缓存未命中时由缓存组件自动从 DB 加载
- 应用不感知数据库的存在

**优点**：应用代码更简洁，DB 访问逻辑收敛到缓存层。
**缺点**：需要支持回源的缓存组件（如 Guava Cache、Caffeine 的 LoadingCache、Redis 的自定义客户端封装）。

### 1.3 Write-Through

应用写操作只写缓存，缓存层同步将数据写入数据库，两者都成功才返回。

- 写缓存 + 同步写 DB 在同一事务内完成
- 强一致性保证，缓存与数据库始终同步

**优点**：数据一致性强，缓存永远是最新的。
**缺点**：写延迟高（需等 DB 写完成）；DB 故障时写也失败。

### 1.4 Write-Behind / Write-Back（回写）

应用只写缓存，缓存层异步将数据刷入数据库。

- 写缓存立即返回，后台线程定时或按策略批量刷新到 DB
- 写延迟极低，适合写密集场景

**优点**：写性能极高，可合并多次写操作。
**缺点**：缓存宕机可能丢失未同步的数据；一致性弱。

### 1.5 四种缓存模式对比

| 模式 | 读路径 | 写路径 | 一致性 | 适用场景 |
|------|--------|--------|--------|---------|
| Cache-Aside | 应用查缓存→未命中查 DB | 应用更新 DB→删缓存 | 最终一致 | 通用，最常用 |
| Read-Through | 应用查缓存，缓存自动回源 | 应用写 DB→删缓存 | 最终一致 | 缓存组件封装 DB |
| Write-Through | 同 Cache-Aside | 应用写缓存，缓存同步写 DB | 强一致 | 写少读多、一致性要求高 |
| Write-Behind | 同 Cache-Aside | 应用写缓存，异步刷 DB | 弱一致 | 写密集、可容忍丢数据 |

## 二、缓存三大问题

### 2.1 缓存穿透（Cache Penetration）

**现象**：查询一个根本不存在的数据（如不存在的商品 ID），缓存和数据库都没有，每次请求都打到数据库。

**原因**：
- 恶意攻击（构造不存在的 ID 大量请求）
- 业务参数校验缺失（如负数 ID、非法 ID）

**解决方案**：

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| null 值缓存 | DB 查不到时缓存空值，设短 TTL（60~300s） | 简单有效，但占内存、需维护过期 |
| 布隆过滤器 | 用 BloomFilter 存合法 ID，请求前先过滤 | 省内存、高效，有误判率、需预热 |
| 参数校验 | 在入口层拦截非法参数（ID 格式、范围） | 第一道防线，治本 |

```
; null 值缓存方案
SET cache:product:9999 "" EX 60

; 布隆过滤器（RedisBloom 模块）
BF.ADD bloom:filter:users 1001
BF.EXISTS bloom:filter:users 9999
```

### 2.2 缓存击穿（Cache Breakdown）

**现象**：某个热点 Key 在过期的瞬间，大量并发请求同时打到数据库。

**原因**：
- 热点数据过期时间到达
- 大量并发查询同一热点 Key

**解决方案**：

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| 互斥锁 | SETNX 抢锁→查 DB→写缓存→释放锁，其他请求等待重试 | 保证只有一个请求回源，但有等待延迟 |
| 逻辑过期 | 不设 TTL，value 内嵌逻辑过期时间，过期后异步刷新 | 不阻塞，但有短暂脏数据 |
| 提前续期 | 后台线程在热点 Key 快过期时主动刷新 | 需额外线程管理 |

```
; 互斥锁方案核心流程
SET lock:cache:product:5001 "uuid" NX EX 10    ; 抢锁
; 抢到锁 → 查 DB → 写缓存
DEL lock:cache:product:5001                     ; 释放锁
```

### 2.3 缓存雪崩（Cache Avalanche）

**现象**：大量 Key 同时过期，或 Redis 宕机，全部请求打到数据库。

**原因**：
- 批量缓存使用相同过期时间，同时失效
- Redis 节点故障

**解决方案**：

| 方案 | 做法 | 适用 |
|------|------|------|
| 随机过期时间 | EXPIRE 时加随机偏移（如 3600 + random(0,600)） | 防批量同时过期 |
| 熔断降级 | 限流 + 返回默认值/降级页面 | 保护 DB |
| Redis 高可用 | 主从 + 哨兵 + 集群 | 防 Redis 宕机 |
| 多级缓存 | 本地缓存 → Redis → DB | 减少对单层依赖 |

### 2.4 三大问题对比表

| 问题 | 原因 | 影响 | 核心解决方案 |
|------|------|------|-------------|
| 缓存穿透 | 查不存在的数据 | 每次请求打 DB | null 值缓存 / 布隆过滤器 |
| 缓存击穿 | 热点 Key 过期瞬间 | 大量并发打 DB | 互斥锁 / 逻辑过期 |
| 缓存雪崩 | 大量 Key 同时过期 / Redis 宕机 | 全部请求打 DB | 随机过期 / 熔断降级 / 高可用 |

> **记忆口诀**：穿透查不到（布隆过滤 + 空值），击穿热 Key 过期（互斥锁），雪崩大批量过期（随机过期 + 高可用）。

## 三、缓存一致性

### 3.1 先更新 DB 后删缓存 vs 先删缓存后更新 DB

| 策略 | 流程 | 风险 |
|------|------|------|
| 先删缓存后更新 DB | 删缓存→更新 DB | 并发读可能把旧 DB 数据回写缓存（脏数据） |
| 先更新 DB 后删缓存 | 更新 DB→删缓存 | 极端并发下删缓存失败导致不一致（概率低） |

**推荐**：先更新 DB 后删缓存（Cache-Aside 标准做法）。

### 3.2 延迟双删

为应对"先删缓存后更新 DB"的脏数据问题，采用延迟双删：

1. 先删除缓存
2. 更新数据库
3. 延迟一段时间（如 500ms，覆盖读流程的最慢耗时）
4. 再次删除缓存

```
; 伪代码
DEL cache:product:1001          ; 第一次删
; UPDATE products SET price=8999 WHERE id=1001
; sleep(500ms)
DEL cache:product:1001          ; 第二次删（清掉并发读回写的脏数据）
```

### 3.3 最终一致性方案

对一致性要求高的场景，用消息队列 + Binlog 订阅实现最终一致：

- **消息队列方案**：更新 DB 后发消息，消费者删除缓存（失败可重试）
- **Binlog 订阅（Canal）**：Canal 订阅 MySQL Binlog，解析变更后自动删除对应缓存

**旁路缓存的一致性保障实践**：
- 写操作统一"先更新 DB 后删缓存"
- 删缓存失败时记录日志 + 重试（或走消息队列补偿）
- 关键业务接受短暂不一致，通过 TTL 兜底最终一致

## 四、分布式锁

### 4.1 为什么需要分布式锁

单机环境下用语言内置锁（如 Java synchronized、Go mutex）即可实现互斥。但在多实例部署（微服务、集群）下，各进程不共享内存，需要借助外部存储（Redis/Zookeeper/etcd）实现跨进程互斥。

**典型场景**：
- 库存扣减（防止超卖）
- 定时任务调度（防止多实例重复执行）
- 限流与配额控制

### 4.2 方案演进

| 版本 | 实现 | 问题 |
|------|------|------|
| v1 | `SETNX key value` + `DEL` | 无过期时间，进程崩溃导致死锁 |
| v2 | `SETNX` + `EXPIRE` | 两步非原子，SETNX 后宕机则锁无过期 |
| v3 | `SET key value NX EX seconds` | 原子加锁，生产可用 |
| v4 | v3 + value 设唯一标识，释放时 Lua 判断 | 防止误删别人的锁 |

```
; v3 正确加锁（原子操作）
SET stock:lock:1001 "uuid-xxx" NX EX 10

; v4 正确释放锁（Lua 脚本保证 GET→比较→DEL 原子）
EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 stock:lock:1001 "uuid-xxx"
```

### 4.3 正确的分布式锁实现

**加锁**：
- `SET stock:lock:{product_id} {uuid} NX EX 10`
- value 必须是全局唯一标识（如 UUID），用于释放时验证归属

**释放锁**：
- 必须用 Lua 脚本：`GET` → 比较 `value == uuid` → `DEL`
- 不能先 GET 再 DEL（两步非原子，可能误删）

**为什么 value 要设唯一标识**：
- 场景：A 加锁（TTL=10s）→ 业务执行 15s → 锁已过期 → B 加锁成功 → A 执行完直接 DEL → 误删了 B 的锁
- 用 Lua 判断 value 可避免误删

### 4.4 锁续期（看门狗机制）

**问题**：TTL 设置两难——太短业务没完成锁就过期（别人能加锁），太长进程崩溃后锁占用久。

**方案**：后台线程定时延长 TTL（看门狗）：
- 加锁后启动看门狗线程，每隔 TTL/3 时间续期一次
- 业务完成后释放锁并停止看门狗

**Redisson 实现**：
- 默认 TTL=30s，每 10s 续期一次
- 支持可重入锁（重入计数）、公平锁、信号量、闭锁

```
; 看门狗续期（Lua 判断 value 匹配后 EXPIRE）
EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('EXPIRE',KEYS[1],ARGV[2]) else return 0 end" 1 stock:lock:1001 "uuid-xxx" 30
```

### 4.5 Redlock 算法

**背景**：主从复制下，主节点加锁后未同步到从节点就宕机，新主没有锁数据 → 锁丢失。

**Redlock 流程**（应对主从切换丢锁）：
1. 客户端记录当前时间 T1
2. 依次向 N 个（通常 5 个）**独立** Redis 实例请求 `SET NX EX` 加锁
3. 超过半数（N/2+1，即 3 个）成功且总耗时 < TTL → 加锁成功
4. 否则向所有实例释放锁，加锁失败

**争议**：
- Martin Kleppmann 认为不安全：GC 暂停或时钟漂移可能导致锁失效
- antirez（Redis 作者）反驳：分布式锁追求效率而非严格正确性
- 实践建议：强一致性场景用 Zookeeper/etcd，高并发效率场景用 Redis 锁

### 4.6 Redisson 简介对比

| 特性 | 手写 Redis 锁 | Redisson |
|------|--------------|----------|
| 加锁 | SET NX EX | RLock.lock() |
| 释放锁 | Lua 脚本 | RLock.unlock() |
| 看门狗续期 | 需自己实现 | 自动续期 |
| 可重入锁 | 需自己实现 | 内置支持 |
| 公平锁 | 不支持 | 内置支持 |
| 信号量/闭锁 | 需自己实现 | 内置支持 |

### 4.7 分布式锁注意事项

- **锁超时设置**：TTL 要大于业务最长执行时间，配合看门狗兜底
- **锁误释放**：必须用 Lua 脚本判断 value 再释放
- **Redlock 争议**：理解其适用边界，不盲信"绝对安全"
- **可重入性**：同一线程/进程多次加锁需计数，避免自死锁

## 五、限流器实现

### 5.1 固定窗口计数器

**原理**：每个时间窗口（如 1 分钟）维护一个计数器，INCR + 首次 EXPIRE。

```
; Lua 实现固定窗口限流
EVAL "local c=redis.call('INCR',KEYS[1]); if c==1 then redis.call('EXPIRE',KEYS[1],ARGV[2]) end; if c<=tonumber(ARGV[1]) then return 'ALLOW' else return 'REJECT' end" 1 rate:limit:user1:api 10 60
```

**缺点**：窗口边界突发流量（59s 打满 + 61s 打满 = 1 秒内双倍流量）。

### 5.2 滑动窗口

**原理**：用 Sorted Set，score=时间戳，每次请求先清理窗口外旧数据再判断计数。

```
; Lua 实现滑动窗口限流
EVAL "redis.call('ZREMRANGEBYSCORE',KEYS[1],0,ARGV[1]-ARGV[2]); local c=redis.call('ZCARD',KEYS[1]); if c<tonumber(ARGV[3]) then redis.call('ZADD',KEYS[1],ARGV[1],ARGV[4]); return 'ALLOW' else return 'REJECT' end" 1 rate:limit:user:api <now> 60 10 <member>
```

**优点**：平滑无突发。**缺点**：内存开销略大。

### 5.3 限流算法对比

| 算法 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| 固定窗口 | INCR + EXPIRE | 实现简单 | 边界突发 |
| 滑动窗口 | ZSET + ZREMRANGEBYSCORE | 平滑无突发 | 内存略大 |
| 令牌桶 | Lua 脚本 | 允许突发、可控速率 | 实现复杂 |
| 漏桶 | 队列 | 严格匀速 | 不允许突发 |

## 七、关键知识点总结

### 缓存模式对比表

| 模式 | 读 | 写 | 一致性 | 推荐 |
|------|----|----|--------|------|
| Cache-Aside | 应用查缓存→未命中查 DB | 更新 DB→删缓存 | 最终一致 | 通用首选 |
| Read-Through | 缓存自动回源 | 更新 DB→删缓存 | 最终一致 | 组件封装 |
| Write-Through | 同上 | 写缓存→同步写 DB | 强一致 | 一致性高 |
| Write-Behind | 同上 | 写缓存→异步刷 DB | 弱一致 | 写密集 |

### 缓存问题速查表

| 问题 | 本质 | 核心方案 |
|------|------|---------|
| 穿透 | 数据不存在 | null 值缓存 / 布隆过滤器 |
| 击穿 | 热点 Key 过期 | 互斥锁 / 逻辑过期 |
| 雪崩 | 大批量失效 | 随机过期 / 熔断降级 / 高可用 |

### 分布式锁演进表

| 版本 | 加锁方式 | 释放方式 | 安全性 |
|------|---------|---------|--------|
| v1 | SETNX | DEL | 可能死锁 |
| v2 | SETNX + EXPIRE | DEL | 非原子死锁 |
| v3 | SET NX EX | DEL | 原子加锁，可能误删 |
| v4 | SET NX EX（唯一 value） | Lua 判断 value | 生产可用 |

### 限流算法对比表

| 算法 | Redis 实现 | 突发流量 | 复杂度 |
|------|-----------|---------|--------|
| 固定窗口 | INCR + EXPIRE | 边界突发 | 低 |
| 滑动窗口 | ZSET | 平滑 | 中 |
| 令牌桶 | Lua 脚本 | 允许突发 | 高 |

## 八、实战练习

### 练习一：缓存击穿互斥锁完整实现

基于 `02-cache-problems.redis` 中的互斥锁方案，编写一个完整的 Lua 脚本，实现以下逻辑：
1. 查询 `cache:product:6001`，命中则直接返回
2. 未命中则尝试加锁 `lock:cache:product:6001`（NX EX 10）
3. 加锁失败返回 `RETRY`，加锁成功则"模拟查 DB"后回写缓存（TTL=3600）并释放锁
4. 验证：连续执行两次脚本，第一次回源写入，第二次直接命中

### 练习二：分布式锁防超卖

模拟秒杀库存扣减场景：
1. 初始化 `stock:product:8001` 为 50
2. 用分布式锁 + Lua 脚本实现：加锁 → 判断库存 > 0 → 扣减 → 释放锁
