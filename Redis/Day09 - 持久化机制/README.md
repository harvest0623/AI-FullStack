# Day09 - 持久化机制

Redis 把全部数据放在内存中，一旦进程退出或服务器断电，内存中的数据会瞬间丢失。如果 Redis 仅作"纯缓存"使用，丢完可以重建；但如果用作数据库、订单系统、计数器，**数据丢失就是生产事故**。持久化机制是把内存数据安全落到磁盘的核心能力，也是 Redis 从"缓存"升级为"数据库"的关键保障。本章系统讲解 Redis 的两种持久化方案——**RDB 快照**与 **AOF 追加**，以及 4.0+ 引入的**混合持久化**，对比三者的取舍，并给出生产环境配置建议。

---

## 学习目标

- 理解为什么 Redis 需要持久化，以及"缓存定位"与"数据库定位"的差异
- 掌握 RDB 快照的工作原理、触发方式、fork + COW 机制
- 掌握 AOF 追加的工作原理、三种刷盘策略（always/everysec/no）
- 理解 AOF 重写的原理、触发条件与重写期间命令的处理
- 掌握 RDB + AOF 混合持久化（4.0+）的优势与配置
- 知道 Redis 启动时的数据恢复流程
- 理解持久化对性能的影响（fork 开销、磁盘 IO）
- 能够为不同业务场景（缓存 / 数据库 / 关键数据）选择合适的持久化策略

## 理论知识讲解

### 一、为什么需要持久化

| 维度 | 内存数据库（无持久化） | 磁盘数据库（MySQL） |
|------|----------------------|-------------------|
| 读写速度 | 极快（10 万+ QPS） | 较慢（千级 QPS） |
| 断电后数据 | **全部丢失** | 持久保留 |
| 容量上限 | 受内存限制（GB 级） | 受磁盘限制（TB 级） |
| 成本 | 内存昂贵 | 磁盘便宜 |

**持久化的意义**：
1. **重启数据恢复**：Redis 进程重启后能恢复到断电前的状态
2. **灾难恢复**：把持久化文件复制到异地或对象存储，应对硬件故障
3. **数据库定位**：让 Redis 不仅是缓存，也能承担"轻量数据库"的角色

**缓存 vs 数据库的定位差异**：
- **纯缓存**：丢数据可接受，从 MySQL 重建即可 → RDB 足矣，甚至关闭持久化
- **数据库**：不能丢数据 → 必须开 AOF everysec，甚至 always

### 二、RDB（Redis Database）快照

#### 2.1 工作原理

RDB 是某个时间点的**全量数据快照**，以二进制压缩格式保存到磁盘的 `dump.rdb` 文件。相当于"给内存拍一张照片"。

#### 2.2 触发方式

| 触发方式 | 命令 / 配置 | 说明 |
|---------|------------|------|
| **手动同步** | `SAVE` | 阻塞 Redis 主进程，期间所有命令无法执行，**生产禁用** |
| **手动异步** | `BGSAVE` | fork 子进程后台生成，主进程继续服务 |
| **自动触发** | `save 900 1` / `save 300 10` / `save 60 10000` | 满足任意条件（N 秒内 M 次修改）自动 BGSAVE |
| **关闭** | `save ""` | 删除所有 save 配置即关闭 RDB 自动触发 |
| **SHUTDOWN** | `SHUTDOWN` | 优雅关闭时默认触发一次 SAVE |
| **主从全量同步** | — | 主节点在复制时会 BGSAVE 发送给从节点 |

**默认 save 配置**（redis.conf）：

```
save 900 1      # 900 秒内至少 1 次修改
save 300 10     # 300 秒内至少 10 次修改
save 60 10000   # 60 秒内至少 10000 次修改
```

#### 2.3 fork 子进程与 COW（Copy-On-Write）

`BGSAVE` 通过 `fork()` 创建子进程写盘，主进程继续对外服务。这依赖操作系统的 **写时复制（Copy-On-Write）** 技术：

```
1. fork() 之前，父子进程共享同一份物理内存页
2. 父进程处理写请求时，内核才复制被修改的页（COW）
3. 子进程看到的是 fork 那一刻的内存快照，不受后续修改影响
```

**潜在风险**：
- **fork 本身耗时**：与内存大小正相关，大实例（>10GB）fork 可能阻塞数百毫秒
- **内存占用翻倍**：极端情况下父子进程所有页都被改写，物理内存翻倍
- 生产建议：单实例内存不超过物理内存的 50%~60%，留足 COW 余量

#### 2.4 RDB 文件格式

- **二进制压缩格式**（默认 LZF 压缩）
- 文件名默认 `dump.rdb`，可通过 `dbfilename` 修改
- 文件小、加载快（直接二进制读入内存）
- **不可读**，无法手工编辑或审计

#### 2.5 优点与缺点

| 优点 | 缺点 |
|------|------|
| ✅ 文件紧凑，体积小 | ❌ 两次快照之间的数据会丢失 |
| ✅ 恢复速度快（二进制加载） | ❌ fork 耗时（大内存实例） |
| ✅ 适合备份与异地容灾 | ❌ 实时性差，无法做到秒级持久化 |
| ✅ fork 子进程不影响主进程 | ❌ COW 极端情况下内存翻倍 |

#### 2.6 核心配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `save` | 见上文 | 触发 BGSAVE 的条件 |
| `dbfilename` | `dump.rdb` | RDB 文件名 |
| `dir` | `./` | 持久化文件存放目录 |
| `stop-writes-on-bgsave-error` | `yes` | BGSAVE 失败时 Redis 拒绝写入，保护数据安全 |
| `rdbcompression` | `yes` | 是否启用 LZF 压缩 |
| `rdbchecksum` | `yes` | 是否在文件末尾加 CRC64 校验和 |
| `rdb-del-sync-files` | `no` | 是否在没有持久化时删除 RDB 文件 |

### 三、AOF（Append Only File）追加

#### 3.1 工作原理

AOF 把每条**写命令**追加到磁盘的 `appendonly.aof` 文件，类似 MySQL 的 binlog。恢复时按顺序重放所有命令重建数据。

```
客户端 SET stock:product:1001 50
            ↓
AOF 文件追加：*3\r\n$3\r\nSET\r\n$17\r\nstock:product:1001\r\n$2\r\n50\r\n
```

#### 3.2 三种刷盘策略

| 策略 | `appendfsync` | 行为 | 数据安全 | 性能 |
|------|--------------|------|---------|------|
| **每条刷盘** | `always` | 每条写命令都 fsync 到磁盘 | 最高（不丢数据） | **最慢** |
| **每秒刷盘** | `everysec` | 每秒 fsync 一次（默认，推荐） | 高（最多丢 1 秒） | 较快 |
| **OS 决定** | `no` | 由操作系统决定何时刷盘 | 最低（可能丢几十秒） | **最快** |

**推荐选择**：`everysec`（默认值）—— 在性能与安全之间取得平衡，最多丢失 1 秒数据，绝大多数业务可接受。

#### 3.3 AOF 重写（Rewrite）

**为什么要重写**：AOF 文件会随命令执行不断膨胀。例如对同一个 key 反复 `INCR`，AOF 会记录每一条，但实际只需保留最终值。

**重写原理**：遍历当前数据库的内存数据，为每个 key 生成**最小命令集**，写入新 AOF 文件，替换旧文件。

例如对 `counter` 执行了 1000 次 `INCR`，重写后会变成一条 `SET counter 1000`。

**触发方式**：

| 方式 | 命令 / 配置 | 说明 |
|------|------------|------|
| **手动触发** | `BGREWRITEAOF` | 类似 BGSAVE，fork 子进程后台重写 |
| **自动触发** | `auto-aof-rewrite-percentage 100` | AOF 文件比上次重写后大一倍时触发 |
| **自动触发** | `auto-aof-rewrite-min-size 64mb` | AOF 文件超过 64MB 才考虑重写 |

**重写期间的新命令处理**：

```
1. fork 子进程开始重写，遍历内存生成新 AOF
2. 主进程继续接收写命令，同时写入：
   - 原 AOF 文件（旧文件，保底）
   - aof_rewrite_buf（重写缓冲区）
3. 子进程写完后，主进程把 aof_rewrite_buf 追加到新 AOF
4. 原子替换旧文件为新文件
```

这样保证重写期间不丢任何新命令。

#### 3.4 优点与缺点

| 优点 | 缺点 |
|------|------|
| ✅ 数据安全性高（everysec 最多丢 1 秒） | ❌ 文件比 RDB 大 |
| ✅ 可读性好，能手工修复 | ❌ 恢复比 RDB 慢（需重放命令） |
| ✅ 可读出每条历史命令，便于审计 | ❌ 重写消耗 CPU 与磁盘 IO |
| ✅ 命令格式兼容，跨版本恢复友好 | ❌ always 策略性能损耗大 |

#### 3.5 核心配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `appendonly` | `no` | 是否开启 AOF |
| `appendfilename` | `appendonly.aof` | AOF 文件名 |
| `appendfsync` | `everysec` | 刷盘策略 |
| `no-appendfsync-on-rewrite` | `no` | 重写期间是否暂停 fsync（避免双倍磁盘 IO） |
| `auto-aof-rewrite-percentage` | `100` | 触发重写的增长比例 |
| `auto-aof-rewrite-min-size` | `64mb` | 触发重写的最小文件大小 |
| `aof-load-truncated` | `yes` | 启动时遇到被截断的 AOF 是否继续加载 |

### 四、RDB + AOF 混合持久化（4.0+）

#### 4.1 痛点

| 方案 | 恢复速度 | 数据安全 |
|------|---------|---------|
| 纯 RDB | 快 | 差（丢失窗口大） |
| 纯 AOF | 慢 | 好（最多丢 1 秒） |

**矛盾**：鱼与熊掌不可兼得。

#### 4.2 混合持久化原理

4.0+ 引入混合持久化，4.4+ 默认开启（`aof-use-rdb-preamble yes`）。

**原理**：AOF 重写时，文件**前半段用 RDB 二进制**（全量快照），**后半段追加增量命令**。

```
┌────────────────────────────────────────────────────────┐
│                    AOF 文件结构                         │
├────────────────────────┬───────────────────────────────┤
│   RDB 二进制段（全量）  │   增量命令段（重写期间新命令）  │
│   快速加载             │   保证数据安全                  │
└────────────────────────┴───────────────────────────────┘
```

**恢复流程**：
1. 先加载 RDB 段，瞬间恢复大部分数据（快）
2. 再重放增量命令段，补齐重写期间的数据（全）

**优势**：兼得 RDB 的恢复速度与 AOF 的数据安全，是当前生产环境的**首选方案**。

#### 4.3 配置

```
aof-use-rdb-preamble yes    # 4.0 引入，4.4+ 默认 yes
```

> 注意：混合持久化只在 AOF 重写时生效。如果 AOF 没有触发过重写，文件仍是纯命令格式。

### 五、数据恢复流程

Redis 启动时的加载顺序：

```
                ┌─────────────────────┐
                │  Redis 进程启动      │
                └──────────┬──────────┘
                           ▼
                ┌─────────────────────┐
                │  AOF 是否开启？      │
                └──────────┬──────────┘
                  开启 │         │ 未开启
                       ▼         ▼
          ┌──────────────────┐   ┌──────────────────┐
          │ 加载 AOF 文件     │   │ 加载 RDB 文件     │
          │ （含混合格式）    │   │ dump.rdb          │
          └──────────────────┘   └──────────────────┘
```

**关键点**：
- AOF 优先级高于 RDB：只要 AOF 开启，启动时就只加载 AOF，忽略 RDB
- 混合持久化文件也是 AOF 文件，按 AOF 流程加载（前段 RDB 快速读入）
- 都不存在时，启动为空数据库

### 六、持久化对性能的影响

| 影响点 | RDB | AOF |
|--------|-----|-----|
| **CPU** | fork 子进程 + LZF 压缩 | 重写时遍历内存 |
| **内存** | COW 可能翻倍 | aof_rewrite_buf 占用 |
| **磁盘 IO** | 写 dump.rdb（间歇） | 每条写命令追加（持续） |
| **fork 阻塞** | 有 | 重写时有 |

**优化建议**：
- 大实例避免频繁 BGSAVE，调大 save 间隔
- AOF 用 everysec，避免 always
- 持久化文件放独立磁盘，避免与日志争抢 IO
- 关注 `INFO persistence` 中的 `latest_fork_usec`

---

### 七、生产配置建议

| 场景 | 推荐配置 | 理由 |
|------|---------|------|
| **纯缓存** | `save ""` + `appendonly no` | 数据可重建，关持久化提升性能 |
| **一般业务缓存** | 默认 RDB（`save 900 1` 等） | 平衡性能与备份 |
| **数据库定位** | AOF everysec + RDB 备份 | 最多丢 1 秒，RDB 用于冷备 |
| **关键数据** | AOF everysec + 混合持久化 + 定期 RDB 冷备 | 兼顾安全与恢复速度 |
| **金融级** | AOF always + 主从复制 + 异地容灾 | 不丢数据，但性能损耗大 |

## 关键知识点总结

### RDB vs AOF 对比表

| 维度 | RDB | AOF |
|------|-----|-----|
| **存储内容** | 全量数据快照 | 写命令日志 |
| **文件格式** | 二进制压缩 | 文本命令（混合模式含 RDB 段） |
| **触发方式** | save 配置 / BGSAVE | appendfsync 策略 |
| **数据安全** | 丢失窗口大 | 最多丢 1 秒（everysec） |
| **恢复速度** | 快 | 较慢（混合模式接近 RDB） |
| **文件大小** | 小 | 大 |
| **CPU 消耗** | fork + 压缩 | 持续追加 + 重写 |
| **可读性** | 不可读 | 可读（便于审计） |
| **适用场景** | 备份、容灾 | 数据库、关键数据 |

### 刷盘策略对比表

| 策略 | 性能 | 安全 | 适用 |
|------|------|------|------|
| `always` | 最慢 | 最高（不丢） | 金融级 |
| `everysec` | 较快 | 高（丢 1 秒） | **推荐**，绝大多数业务 |
| `no` | 最快 | 最低 | 可丢数据的缓存 |

### 生产配置建议表

| 业务等级 | RDB | AOF | 混合 | 备注 |
|---------|-----|-----|------|------|
| 纯缓存 | 关 | 关 | — | 重建即可 |
| 普通缓存 | 开 | 关 | — | 默认配置 |
| 一般数据库 | 开 | everysec | yes | 推荐 |
| 关键数据 | 开 | everysec | yes | 加定期冷备 |
| 金融级 | 开 | always | yes | 加主从+异地 |

### 混合持久化原理

```
AOF 重写时：
  ┌─────────────────────────────────────┐
  │  新 AOF 文件                        │
  │  ┌────────────┬───────────────────┐  │
  │  │ RDB 二进制  │ 增量命令          │  │
  │  │ （全量快照）│ （重写期间新写入） │  │
  │  └────────────┴───────────────────┘  │
  └─────────────────────────────────────┘
  恢复时：先加载 RDB 段（快），再重放命令段（全）
```

## 实战练习

### 练习 1：观察 BGSAVE 对内存与延迟的影响

需求：
1. 用脚本写入 100 万条测试数据（`SET test:k1 v1` ... `SET test:k1000000 v1`）
2. 执行 `BGSAVE`，立即用 `INFO persistence` 查看 `rdb_bgsave_in_progress` 是否为 1
3. 用 `INFO stats` 查看 `latest_fork_usec`，评估 fork 耗时
4. 思考：如果实例内存为 10GB，fork 会阻塞多久？

提示：
```bash
# 批量写入（用管道加速）
for i in $(seq 1 1000000); do echo "SET test:k$i v$i"; done | redis-cli --pipe

redis-cli BGSAVE
redis-cli INFO persistence | grep -E "rdb_bgsave|latest_fork"
```

### 练习 2：对比 always 与 everysec 的性能差异

需求：
1. 开启 AOF，设置 `appendfsync always`
2. 用 `redis-benchmark` 写入 1 万条数据，记录 QPS
3. 改为 `appendfsync everysec`，重复测试
4. 对比两次 QPS 差距

提示：
```bash
redis-cli CONFIG SET appendonly yes

redis-cli CONFIG SET appendfsync always
redis-benchmark -t set -n 10000 -q

redis-cli CONFIG SET appendfsync everysec
redis-benchmark -t set -n 10000 -q
```

思考：为什么 `always` 性能差这么多？什么场景下值得用？

### 练习 3：模拟灾难恢复

需求：完整演练一次"写入 → 备份 → 模拟故障 → 恢复"流程：

1. 写入若干测试数据（如 `SET order:1001 "user_a"`）
2. 执行 `BGSAVE`，把 `dump.rdb` 复制到备份目录
3. `FLUSHALL` 清空数据，模拟误操作
4. 停止 Redis，用备份的 `dump.rdb` 替换工作目录文件
5. 重启 Redis，验证数据是否恢复
6. 思考：如果只开了 AOF，恢复流程有何不同？

提示：在 Docker 中操作更安全：
```bash
docker exec redis-learn redis-cli BGSAVE
docker cp redis-learn:/data/dump.rdb ./backup-dump.rdb
docker exec redis-learn redis-cli FLUSHALL
docker stop redis-learn
docker cp ./backup-dump.rdb redis-learn:/data/dump.rdb
docker start redis-learn
docker exec redis-learn redis-cli GET order:1001
```
