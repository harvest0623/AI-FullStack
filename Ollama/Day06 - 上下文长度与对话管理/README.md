# Day06 - 上下文长度与对话管理

## 为什么需要上下文管理

| 问题现象 | 原因 | 后果 |
|---------|------|------|
| 聊着聊着"忘了"前面的事 | 对话被截断 | 上下文丢失 |
| 请求报「context length exceeded」 | 超出 num_ctx | 请求失败 |
| 回答越来越慢 / 占显存大 | 上下文越长计算/显存越高 | 性能下降 |
| token 浪费（重复携带历史） | 未裁剪 | 成本与延迟上升 |

**根因**：模型一次能处理的 token 数有限（num_ctx），而对话历史是持续累积的。对话管理 = 决定"带多少历史、怎么带"。

---

## 核心概念

- **num_ctx**：上下文窗口大小（token 数），Ollama 默认 2048；可调大（越大越能装长文，越吃显存/越慢）。
- **多轮对话**：把 `user`/`assistant` 消息按顺序放进 `messages` 传给 `/api/chat`。
- **会话隔离**：不同用户/场景各自维护独立的历史，互不串扰。
- **历史裁剪**：超出窗口时去掉最早的消息，只保留最近 N 轮。
- **历史摘要**：裁剪的同时用一句摘要压缩旧信息，兼顾"记忆"与"长度"。
- **与记忆系统衔接**：这里的"对话历史"就是 Agent 板块的**短时/工作记忆**来源。

## 每日内容详解

### 01 - num_ctx 与 token 统计
用纯规则的方式讲清**上下文窗口如何工作**：列出模型一次能看的"词汇量"，模拟填入历史与输入，计算已用与剩余。

### 02 - 多轮对话历史构建
演示 messages 的顺序累加：`system` 定位 + 连续 `user/assistant` 回合，每次新问题都带上全部历史，看模型如何"记住"。

### 03 - 会话隔离
用字典把 `session_id → history` 分开管理，两个"用户"各自有独立记忆，互不覆盖——这是多用户服务端的基础。

### 04 - 历史裁剪与摘要
实现"窗口感知"：token 超限时丢弃最早回合；再用一句摘要代替被丢弃的旧内容，兼顾长度与记忆。

## 练习与挑战

1. **token 预估**：给定 `num_ctx=2048` 和历史脚本，估算还剩多少余量。
2. **会话池**：把 `03` 的字典改造成按用户自动创建/复用会话。
3. **混合策略**：最近 5 轮全保留 + 更早的压成摘要（滑动窗口 + 摘要）。
4. **真实验证**：启动 Ollama，调大 num_ctx 试一段长文，对比 2048 与 8192 的差异。

## 知识点速查

| 项 | 说明 |
|----|------|
| 默认 num_ctx | 2048 token |
| 调大 num_ctx | 能装更多历史，但更慢/更吃显存 |
| messages 结构 | `[{"role","content"},…]`，按时间顺序 |
| 会话隔离 | 每用户/每场景独立 history |
| 裁剪策略 | 窗口超限 → 去掉最早回合 |
| 摘要策略 | 用短摘要压缩长旧历史 |
| 与 Agent 衔接 | 历史 ≈ 短时记忆；摘要 ≈ 简化长期记忆 |
