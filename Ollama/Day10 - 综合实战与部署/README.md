## 为什么需要综合实战

前面每天学一个点，实战把点串成线：一个能用的本地应用需要**同时**会对话、记得住、会查知识库、能调工具、能对外服务、能控性能。今天用一个小而完整的应用验证组合能力。

---

## 核心概念

- **全链路整合**：Chat（对话）+ Memory（记忆）+ RAG（检索知库）+ Tools（工具）组合。
- **服务化**：把应用封装成 HTTP 接口，供前端/其他服务调用（示例用 Flask/自写 HTTP）。
- **GPU 检测**：`ollama ps` / 硬件探测判断能否加速推理。
- **性能基准**：测单请求延迟、吞吐（QPS），用于调参（num_ctx、并发数）。
- **生产考虑**：会话隔离、超时、并发、显存、日志，以及"本地 vs 云"权衡。

---

## 今日学习目标

- 检测本机硬件与 Ollama 能力（GPU/模型）
- 组装一个本地智能客服（对话+记忆+RAG+工具）
- 用 HTTP 把已知应用服务化，暴露聊天端点
- 做一个简单性能基准，理解影响延迟/吞吐的因素
- 掌握本地部署的注意事项

---

## 每日内容详解

### 01 - GPU 与硬件检测
`nvidia-smi` / CPU 探测，`ollama ps` 看已加载模型，判断本机能跑多大模型。

### 02 - 综合客服实战
组装一个 `AgentLee`：有会话记忆、能从知识库检索（RAG）、能调工具（查订单/算数）。真实/模拟双模式。

### 03 - 服务化
用标准库的 HTTP 服务器把客服包装成 `/chat` 接口，支持 POST JSON（session_id + message），返回回复。

### 04 - 性能基准
测 N 次请求的平均延迟、QPS、错误率，对比不同 num_predict / 并发的结果，给出调优结论。

---

## 练习与挑战

1. **加接口**：在 03 加一个 `/health` 健康检查端点。
2. **并发提参**：用线程并发请求，对比 1 / 4 / 8 并发下的吞吐。
3. **观测日志**：给服务加请求计数与耗时日志。
4. **试真模型**：有 Ollama 时 pull llama3.1 跑 02，观察真实回答质量。
